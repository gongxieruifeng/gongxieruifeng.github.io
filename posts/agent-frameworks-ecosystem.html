Agent 是什么：从公式到类比

各家对 Agent 的定义细节不尽相同，但落到工程实现上，可以用一个公式概括它的组成：

Agent = LLM + Memory + Tools + Planning + Action
LLM 提供决策和推理能力，Planning 把目标拆解成可执行的步骤，Tools 负责对接外部世界完成具体操作，Memory 保存对话和任务上下文，Action 是最终落地的执行动作——五者共同构成一个能自主完成任务的智能体，而不只是一个问答机器人。

一个比较直观的类比是"打车去西藏玩"这件事：

公式组件类比角色具体表现
LLM大脑中枢规划这趟行程的"你"这个决策主体
Planning规划步骤一：规划打车路线；步骤二：定饭店、订酒店……
Tools调用工具调用 MCP 或 Function Calling 等接口——滴滴打车、携程 / 美团订酒店饭店
Memory记忆能力沟通时要知道上下文，比如订酒店得记住是在去西藏路上的哪一段
Action执行真正完成下单、支付这些落地操作

这个类比的价值在于把五个抽象组件全部对应到一次真实决策链路上：LLM 负责"想清楚"，Planning 负责"拆步骤"，Tools 负责"调外部能力"，Memory 负责"不丢上下文"，Action 负责"真正把事办成"。后面几节要讨论的所有框架、协议、平台，本质上都是在工程化地实现或组合这五个组件。

开发框架层：从单智能体执行范式到多智能体编排

Planning 具体怎么落地，业界沉淀出几种可复用的执行范式；当任务复杂到需要多个角色协作时，又演化出 AutoGen、CrewAI 这类多智能体编排框架。这一节按"单智能体范式 → 多智能体编排"的顺序展开。

单智能体的四种执行范式

这几种范式都基于 LangChain 生态实现，核心差异在于"怎么组织 LLM 的思考步骤"，适用场景也各不相同。

Plan-and-Execute：先规划，后执行

先综合考虑任务的多个方面产出一份完整计划，再按计划逐步执行，适合复杂项目管理或需要多步决策的场景。

from langchain_openai import ChatOpenAI
from langchain_experimental.plan_and_execute import PlanAndExecute, load_agent_executor, load_chat_planner
from langchain import SerpAPIWrapper, LLMMathChain
from langchain.agents.tools import Tool

llm = ChatOpenAI()
search = SerpAPIWrapper()
llm_math_chain = LLMMathChain(llm=llm, verbose=True)

tools = [
    Tool(name="Search", func=search.run, description="用于回答关于当前事件的问题"),
    Tool(name="Calculator", func=llm_math_chain.run, description="用于计算或解决问题"),
]

planner = load_chat_planner(llm)
executor = load_agent_executor(llm, tools, verbose=True)
agent = PlanAndExecute(planner=planner, executor=executor, verbose=True)

agent.run("在纽约，100美元能买几束玫瑰？")

Self-Ask：自问自答，拆解复杂问题

允许模型对自己提出中间问题并逐一回答，以增强对原问题的理解、提高最终答案质量，适合需要深入分析或创造性解决方案的场景，比如创意写作。

from langchain import hub
from langchain.agents import AgentExecutor, create_self_ask_with_search_agent
from langchain_community.tools.tavily_search import TavilyAnswer
from langchain_fireworks import Fireworks

llm = Fireworks(model="accounts/fireworks/models/llama-v3p1-405b-instruct", max_tokens=256)
tools = [TavilyAnswer(max_results=1, name="Intermediate Answer")]

prompt = hub.pull("hwchase17/self-ask-with-search")
agent = create_self_ask_with_search_agent(llm, tools, prompt)
agent_executor = AgentExecutor(agent=agent, tools=tools, verbose=True, handle_parsing_errors=True)

agent_executor.invoke({"input": "上一届的美国总统是谁?"})

ReAct：思考 - 行动 - 观察的循环

在 LangChain 里用 Agent 时需要理解四个核心元素：llm（提供逻辑的引擎，负责生成预测和处理输入）、prompt（指导模型形成推理框架）、tools（外部工具，涵盖数据增强、清洗、搜索、API 等）、Agent Executor（负责调用合适的外部工具并管理整个流程）。ReAct 的核心是让模型在 Thought → Action → Observation 之间循环，直到能给出 Final Answer。

from langchain_openai import ChatOpenAI
from langchain_community.agent_toolkits.load_tools import load_tools
from langchain.prompts import PromptTemplate
from langchain.agents import create_react_agent, AgentExecutor

llm = ChatOpenAI(model='gpt-4-turbo-preview', temperature=0.5)
tools = load_tools(["serpapi", "llm-math"], llm=llm)

template = '''尽你所能用中文回答以下问题。如果能力不够你可以使用以下工具:

{tools}

Use the following format:

Question: the input question you must answer
Thought: you should always think about what to do
Action: the action to take, should be one of [{tool_names}]
Action Input: the input to the action
Observation: the result of the action
... (this Thought/Action/Action Input/Observation can repeat N times)
Thought: I now know the final answer
Final Answer: the final answer to the original input question

Question: {input}
Thought:{agent_scratchpad}'''
prompt = PromptTemplate.from_template(template)

agent = create_react_agent(llm, tools, prompt)
agent_executor = AgentExecutor(agent=agent, tools=tools, handle_parsing_errors=True, verbose=True)

agent_executor.invoke({"input": "目前市场上玫瑰花的一般进货价格是多少？如果我在此基础上加价5%，应该如何定价？"})

Reflection：执行 - 反思 - 优化的自我迭代

反思机制被越来越多地集成到 Agent 的决策循环中，核心思想是在 Agent 完成一次任务或一个重要步骤后，引入一个"反思"环节：

  1. Agent 执行任务并生成一个初步结果
  2. Agent（或另一个"批判家"Agent）评估这个结果是否完整、准确，是否存在逻辑错误或更优解
  3. 基于反思得出的改进意见，Agent 修改计划或行动并重新执行，产出更高质量的最终结果

这种"行动 - 反思 - 优化"的循环让 Agent 具备了在没有人类监督时自我迭代的能力，Reflexion 和 LATS（Language Agent Tree Search）是这一思想的代表性实践。

这四种范式在实践中并非互斥，而是可以组合使用：先用 Plan-and-Execute 制定宏观计划，在执行每个宏观步骤时用 ReAct 处理细节，并在关键节点后引入 Reflection 进行检查和优化，从而集各家之所长。这套"宏观规划 + 细节循环 + 关键节点反思"的组合模式，我在参与的 GeoME（时空预测方向）相关工作中也验证过其可行性。

AutoGen：层级式多智能体架构

AutoGen 可以轻松搭建层级式架构的多智能体系统——由一个协调节点统一管理多个专业 Agent，这和 LangGraph 生态中 langgraph-supervisor 依赖库里 supervisor-Agent 的思路是一致的。

它的核心优势在于：模拟测试团队多角色配合的多智能体协作能力、以自然语言交互降低使用门槛的对话驱动模式、便于集成现有工具和框架的灵活扩展性，以及微软背书下活跃、完善的开源生态。落到具体产品形态上，AutoGen 把这套能力拆成几个可视化模块：Models 模块负责接入本地（如 Ollama）或在线的 LLM 服务；Agents 模块用来配置普通成员 Agent 和小组管理员 Agent；Skills 模块可以为 Agent 导入额外能力；Workflows 模块则通过配置用户输入触发器、并指定一个 Agents 模块中配置好的管理员 Agent 作为 Manager 节点，组装出一条完整的多智能体工作流。

CrewAI：平等式角色分工架构

CrewAI 是一个精简、快速的 Python 框架，从零开始构建、不依赖 LangChain 或其他代理框架，走的是一种平等式架构的多智能体路线。它通过模拟现实世界中的"团队分工"模式，让每个智能体拥有明确角色、目标和技能，能自主委派任务、共享信息，核心目标是协调多个 AI 智能体协作完成复杂任务，实现"1+1>2"的协作效果。

核心优势体现在五个方面：角色驱动设计（每个智能体有明确角色、目标和背景故事，LLM 能更精准定位任务需求）、智能协作能力（智能体间自主委派任务、共享上下文，无需人工干预）、灵活工具集成（支持网络搜索、PDF 解析、向量数据库检索等工具）、生产级就绪（内置内存管理、知识库、可观测性和安全机制）、低门槛使用（简洁 API + YAML 配置，新手也能快速搭建）。典型应用场景包括内容创作（研究员收集资料 → 撰稿人撰写 → 编辑审核）、市场分析（数据采集 → 分析师提炼趋势 → 报告生成）、客户支持（客服解答基础问题 → 技术专家处理复杂故障 → 跟进反馈）等。

组件作用关键属性
Agent（智能体）执行具体任务的"团队成员"role / goal / backstory / tools / llm
Task（任务）智能体需完成的具体工作单元description / agent / expected_output / context
Crew（团队）组织智能体和任务的协调者agents / tasks / process / verbose
Flow（流程）精细化控制任务流，支持条件逻辑、循环@start / @listen / @router / 状态持久化
Tool（工具）智能体执行任务的"武器"通过 @tool 装饰器封装

以一个"PDF 成绩查询助手"为例：检索智能体优先从 PDF 中提取成绩信息，若无结果则调用网络搜索；响应合成智能体把检索结果整理成自然语言回答；两者由 Crew 按 Process.sequential 顺序执行。角色和任务用 YAML 与代码分离配置，改角色描述不用碰代码：

# config/agents.yaml
retriever_agent:
  role: >
    成绩信息检索专家: {query}
  goal: >
    从可用资源中检索与用户查询{query}最相关的成绩信息，优先使用PDF搜索工具；
    若PDF无结果，再使用网络搜索工具补充。
  backstory: >
    你是一位细致的教育数据分析师，擅长从文档和网络中精准提取学生成绩信息，
    熟悉成绩单格式，能快速定位姓名、班级、分数等关键信息。
from crewai import Agent, Crew, Process, Task, LLM
from crewai.project import CrewBase, agent, crew, task
import os

def deepseek_llm():
    return LLM(
        model="deepseek/deepseek-chat",
        api_key=os.getenv("DEEPSEEK_API_KEY"),
        base_url="https://api.deepseek.com/v1",
        model_kwargs={"llm_provider": "deepseek"}
    )

@CrewBase
class GradeQueryCrew:
    agents_config = "../config/agents.yaml"
    tasks_config = "../config/tasks.yaml"

    @agent
    def retriever_agent(self) -> Agent:
        return Agent(config=self.agents_config['retriever_agent'],
                     tools=[pdf_tool, ddgs_text_search], llm=deepseek_llm())

    @agent
    def response_synthesizer_agent(self) -> Agent:
        return Agent(config=self.agents_config['response_synthesizer_agent'], llm=deepseek_llm())

    @task
    def retrieval_task(self) -> Task:
        return Task(config=self.tasks_config['retrieval_task'])

    @task
    def response_task(self) -> Task:
        # context 显式声明依赖：先检索，再合成
        return Task(config=self.tasks_config['response_task'],
                    context=[self.retrieval_task()], output_file='成绩查询结果.md')

    @crew
    def crew(self) -> Crew:
        return Crew(agents=self.agents, tasks=self.tasks, process=Process.sequential, verbose=True)

协议层：MCP、Function Calling 与 Agent Skills

Tools 这一环要落地，光有框架不够，还需要"模型怎么发现工具""模型怎么调用工具"的统一规范——这正是 MCP、Function Calling 和 Agent Skills 三者共同覆盖、又各自分工的问题。

MCP 协议：把 M×N 问题变成 M+N 问题

MCP（Model Context Protocol，模型上下文协议）是 2024 年 11 月底由 Anthropic 推出的一种开放标准，目标是让应用程序以统一的方式向大语言模型提供工具调用能力，极大简化了大语言模型与外部世界的交互方式。

在 MCP 之前，为每个数据源单独构建连接是一个 M × N 问题——M 个应用对接 N 个数据源，就要写 M×N 套集成代码，架构碎片化、难以扩展，限制了 AI 获取上下文信息的能力。MCP 提供统一且可靠的访问方式后，这个问题变成了 M + N：每个应用只需对接 MCP 协议一次，每个数据源只需实现一个 MCP Server。

MCP 遵循客户端 - 服务器架构：

角色定位
MCP Host运行 MCP 的主应用程序（如 Claude Desktop、Cursor、Cline），为用户提供与 LLM 交互的界面，同时集成 MCP Client 以连接 MCP Server
MCP Client嵌入在 Host 中，充当 LLM 与 MCP Server 之间的桥梁：接收 LLM 请求 → 转发给对应 Server → 把结果返回给 LLM
MCP Server提供一组特定工具，负责从本地数据或远程服务中检索信息；本质是运行在电脑上的一个 Node.js 或 Python 程序——TypeScript 写的通过 npx 运行，Python 写的通过 uvx 运行，可以理解为客户端用命令行调用了本地程序
本地 / 远程资源MCP Server 实际读取或操作的数据源，可以是本地文件系统，也可以是远程 API

通信机制上，MCP 目前支持两种传输方式：

机制适用场景特点
stdio（标准输入输出）本地服务，操作本地软件或文件，比如没有在线服务的 Blender，是 MCP 默认的通信方式无需外部网络依赖，速度快、可靠性高、易调试；但配置较复杂（需预装命令行工具），单进程通信，无法并行处理多个客户端请求
SSE（Server-Sent Events）远程在线服务，比如访问邮箱、查天气这类本身就有在线 API 的场景配置简单，一个连接地址就能用，适合实时数据更新、消息推送、轻量级监控和日志流；缺点是长连接一旦中断或波动容易丢数据
Streamable HTTP网络不够稳定的远程服务场景支持按会话 ID 重新建立 SSE 流，网络恢复后接续执行之前未完成的传输，解决了 SSE 的稳定性问题

MCP 的核心 API 只有两个：tools/list（列出 Server 支持的所有工具）和 tools/call（Client 请求 Server 执行某个工具并返回结果）。另外，应用层还有一个 A2A（Agent-to-Agent）协议，设计目的是让不同平台上的 Agent 之间能以自然的方式协作，例如阿里云上创建的 Agent 可以通过 A2A 协议与火山云上创建的 Agent 无缝通信协作——这解决的是 Agent 与 Agent 之间的互联问题，和 MCP 解决 Agent 与工具之间互联的问题是两个层面。

Function Calling 与 MCP：能力与协议的关系

Function Calling 指的是模型具备调用函数的能力，这个能力不是函数和服务器之间的沟通能力，而是模型（或者更准确地说，模型对应的 API）和服务器之间的沟通能力——毕竟很多模型是闭源的，我们直接用的往往是模型 API 与服务提供商服务器之间的这层交互。

两者不在同一层面，不是竞争关系：MCP 规定的是 MCP Server 和 MCP Client 之间如何通信，即如何发现和调用函数，这套规范和模型本身无关；Function Calling 是模型的一种能力，是大模型告诉服务器（或代理）"这个任务可以调用某个工具"的决策能力。换句话说，大模型只扮演"大脑"的角色——给出该调用什么工具的方案，但并不能真正执行调用，真正的调用和执行是由服务器 / 代理完成的，而 MCP 正是规范这层执行怎么发生的协议。

Agent Skills：渐进式披露的另一种工具供给范式

Skills 的本质是一个特殊命名的文件夹（约定名为 skills），里面包含每个技能的 SKILL.md 简要说明文档、对应的详细参考文档，以及技能可以调用的脚本文件（比如查询网页、数学运算、操作本地文件系统的能力）：

pdf-processor/                     # Skill 根目录，名称需与 name 字段一致
├── SKILL.md                       # 核心文件，包含元数据和操作指南
├── scripts/                       # 存放可执行脚本
│   └── extract_pdf.py
└── references/                    # 存放参考资料
    └── api_docs.md
文件 / 目录角色与内容生效时机
SKILL.md（YAML 头）技能的"身份牌"：name、description、allowed-tools 等元数据始终常驻，Agent 启动时自动预加载到系统提示，用于快速识别和匹配任务
SKILL.md（正文）技能的"操作手册"：详细步骤、工具用法、约束规则按需加载，Agent 判断任务相关时才读取全文
scripts / references / assets技能的"工具箱与资料库"：可执行脚本、参考文档、模板按需引用，仅在 SKILL.md 指令中明确要求时才被读取或执行

这套渐进式披露策略的核心是分层加载：初始阶段只加载所有技能的 name 和 description，用很少的 token 让模型知道自己"持有哪些技能"；需要用到某个技能时，才进一步加载它的 SKILL.md 了解细节；真正执行时，再按 SKILL.md 里的指引去读取更细粒度的参考文档或脚本。相比 MCP 需要在模型上下文中全量注册所有工具的信息，这套策略解决了两个实际问题：一是简单任务场景下，大量工具信息仍要占用上下文，造成 token 浪费；二是大量工具注册容易导致模型注意力涣散，即便是能力更强的模型，正确理解任务并调用对应工具的压力也会增大。Skill 的漏斗式引导让模型只关注当下最相关的能力，同时书写一个 Skill 的门槛也远低于实现一个 MCP Server。

三者分工清晰：MCP 解决"多个工具如何被统一接入"的协议标准化问题，Function Calling 是模型本身"决定调用哪个工具"的能力，Agent Skills 解决的是"大量工具信息如何不淹没上下文"的组织效率问题。三者不互斥，一个成熟的 Agent 系统往往同时依赖这三层。

低代码 / 无代码平台：Dify 与 Coze

当以上这些能力需要快速交付给业务方使用时，低代码平台把"选模型、接知识库、配工具、编排流程"都变成了可视化操作，Dify 是其中比较有代表性的一个。

Dify：知识库、Function Calling 与工作流的可视化编排

本地部署走的是标准 Docker Compose 路径：克隆仓库、把 .env.example 复制为 .env、执行 docker compose up -d 拉起全部服务，几分钟就能在本地访问控制台完成注册登录。

知识库是 Dify 里最基础的能力之一：创建知识库、上传文档完成切片和向量化之后，把它挂载给某个应用，应用在回答问题时就能引用知识库内容作为依据，而不是仅依赖模型的参数记忆——这也是没挂知识库和挂了知识库之后，同一个应用回答质量差异最直观的来源。

除了知识库，Dify 也支持接入自定义 Function Calling 工具。比如用 FastAPI 包一个天气查询接口，核心逻辑是校验请求头里的 Authorization、按城市名查编码、请求外部天气 API 并解析成自然语言：

from fastapi import FastAPI, Request, HTTPException
from pydantic import BaseModel
import requests

app = FastAPI()
VALID_TOKEN = "your-token-here"
CITY_CODES = {"北京": "101010100", "上海": "101020100"}

class WeatherRequest(BaseModel):
    location: str

@app.post("/weather")
def get_current_weather(request: Request, body: WeatherRequest):
    auth_header = request.headers.get("Authorization")
    if auth_header != f"Bearer {VALID_TOKEN}":
        raise HTTPException(status_code=403, detail="Invalid Authorization header")

    city_code = CITY_CODES.get(body.location)
    if not city_code:
        return {"status": "error", "message": f"暂不支持 {body.location}，目前支持：{','.join(CITY_CODES.keys())}"}

    url = f"http://t.weather.itboy.net/api/weather/city/{city_code}"
    try:
        data = requests.get(url, timeout=10).json()
        forecast = data["data"]["forecast"][0]
        high = forecast["high"].replace("高温 ", "")
        low = forecast["low"].replace("低温 ", "")
        return f"{body.location}今天是{forecast['type']}，温度{high}/{low}"
    except Exception as e:
        return {"status": "error", "message": f"天气数据获取失败: {str(e)}"}

本地起服务后用 localtunnel（lt --port 8081）做一层公网穿透方便调试，拿到公网地址后，把接口的 OpenAPI Schema 粘贴到 Dify「插件」→「创建插件」页面，配置好 Authentication 请求头、测试通过后启用，就能在应用的「工具」面板里勾选这个插件，让 Agent 在识别到天气相关问题时自动调用：

用户输入：北京今天天气怎么样？
Agent 回复：让我帮您查询北京的天气...
          北京今天是多云，温度32℃/22℃

用户输入：上海明天会下雨吗？
Agent 回复：我只能查询当前天气，无法预测明天。当前上海的天气是：上海今天是晴，温度35℃/28℃

Dify 里编排应用有两种模式，选型的核心是看任务需要"确定性"还是"灵活性"：

维度工作流（Workflow）智能体（Agent）
流程控制固定不变，显式定义自主决策，动态规划
可预测性★★★★★★★★☆☆
灵活性★★★☆☆★★★★★
运行成本低（Token 消耗可控）高（多轮推理消耗大）
调试难度容易（路径清晰）困难（黑盒决策）

应用编排完成后，可以通过 Service API 对外暴露：Base URL 固定为 http(s)://your-dify-host/v1，鉴权走 API-Key，所有请求都要在 Authorization HTTP Header 中携带，格式为 Authorization: Bearer app-*********，强烈建议把 API-Key 放在后端存储而不是客户端或前端代码里，避免泄露导致损失。

Coze：与 Dify 高度同源的另一条低代码路径

Coze 的使用方式和操作流程与 Dify 高度类似，知识库配置、Function Calling 工具接入、Workflow / Agent 编排这些核心概念可以直接从 Dify 的使用经验中迁移过来，这里不再展开。

工作流保证确定性和成本可控，Agent 保证灵活性；实践中更常见的做法是两者混合——用工作流兜住主干流程，在需要动态决策的节点上嵌入一个 Agent 子节点，兼顾可控性和应变能力。
