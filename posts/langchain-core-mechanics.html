Model I/O：统一的模型调用接口

LangChain 对接的模型分三类：LLMs（基于海量文本训练、面向文本生成的基础模型）、Chat Models（在 LLM 基础上针对多轮对话场景优化）、Embeddings Models（把文本转成向量）。三者的输入输出形态不同，但 LangChain 给它们套了同一层调用接口：invoke()、stream()、batch()，以及对应的异步版本 ainvoke()、astream()。

一个容易踩的细节是返回类型不同：纯 LLM 的 invoke()/stream() 直接返回字符串；Chat Model 返回的是 AIMessage 对象，需要取 response.content 才能拿到文本。聊天场景下，消息按角色区分——SystemMessage（设定背景/角色）、HumanMessage（用户输入）、AIMessage（模型回复）——可以整体作为一个列表传入 invoke()，表示完整的对话历史：

from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

conversation = [
    SystemMessage("你是一个将英语翻译成法语的有用助手。"),
    HumanMessage("翻译：我喜欢编程。"),
    AIMessage("J'adore la programmation."),
    HumanMessage("翻译：我喜欢构建应用程序。")
]

response = model.invoke(conversation)
print(response)  # AIMessage("J'adore créer des applications.")

stream() 返回一个迭代器，边生成边产出内容块，对长回复的体验提升明显；对支持推理/工具调用的模型，还可以按块类型分别处理：

for chunk in model.stream("天空是什么颜色？"):
    for block in chunk.content_blocks:
        if block["type"] == "reasoning" and (reasoning := block.get("reasoning")):
            print(f"推理：{reasoning}")
        elif block["type"] == "tool_call_chunk":
            print(f"工具调用块：{block}")
        elif block["type"] == "text":
            print(block["text"])

batch() 则用于一次性并发处理多组独立输入，接收 list[list[消息]]，返回 list[AIMessage]，适合离线批量任务而不是单轮对话。同步调用（invoke）逐个执行、总耗时是各步骤之和；异步调用（ainvoke/astream）在等待网络 I/O 时可以让程序继续做别的事，批量请求外部模型 API 时收益明显。

Prompt 模板体系：从模板到 Runnable

PromptTemplate 把固定的提示词改造成可插值的字符串模板：以字典作为输入填充变量，输出一个 PromptValue，可以再转成字符串或消息列表。prompt | model 这个写法本质就是"用输入填模板 → 把完整提示传给模型 → 拿到生成结果"这三步的串联，是 LangChain 里最基础的组合方式。

Few-shot：把示例塞进提示词

少样本提示可以显著提升模型在特定任务上的表现。字符串场景用 FewShotPromptTemplate，聊天场景则用专门优化过的 FewShotChatMessagePromptTemplate——它会自动把示例格式化成 HumanMessage/AIMessage，保留对话轮次结构：

from langchain.prompts import FewShotChatMessagePromptTemplate, ChatPromptTemplate

examples = [
    {"input": "1+1等于几？", "output": "1+1等于2"},
    {"input": "法国的首都是？", "output": "巴黎"}
]

msg_example_prompt = ChatPromptTemplate.from_messages([
    ("human", "{input}"),
    ("ai", "{output}"),
])

few_shot_prompt = FewShotChatMessagePromptTemplate(
    example_prompt=msg_example_prompt,
    examples=examples)

如果示例库很大，没必要每次都把全部示例塞进提示词——用 Example selectors 按当前输入动态挑选最相关的子集：语义相似选择（余弦相似度取 top-k）、长度选择（按输入长度匹配，比语义计算更轻量）、最大边际相关（MMR，兼顾相关性和多样性，避免选出的示例同质化）。语义相似选择的典型用法：

from langchain_community.vectorstores import FAISS
from langchain_core.example_selectors import SemanticSimilarityExampleSelector
from langchain_core.prompts import FewShotPromptTemplate, PromptTemplate
from langchain_openai import OpenAIEmbeddings

examples = [
    {"input": "高兴", "output": "悲伤"},
    {"input": "高", "output": "矮"},
    {"input": "长", "output": "短"},
]

embeddings = OpenAIEmbeddings(model="text-embedding-ada-002")

example_selector = SemanticSimilarityExampleSelector.from_examples(
    examples, embeddings, FAISS, k=2)

similar_prompt = FewShotPromptTemplate(
    example_selector=example_selector,
    example_prompt=PromptTemplate.from_template("Input: {input} \n Output: {output}"),
    prefix="给出每个词组的反义词",
    suffix="Input: {word}\nOutput:",
    input_variables=["word"])

ChatPromptTemplate 与消息占位符

多轮对话场景下，ChatPromptTemplate.from_messages() 配合 MessagesPlaceholder 可以把一段历史消息整体注入到提示词的某个位置，而不用手写拼接：

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

chat_prompt_template = ChatPromptTemplate.from_messages(
    [
        ("system", "你是一个边塞诗人，可以作诗。"),
        MessagesPlaceholder("history"),
        ("human", "请再来一首唐诗"),
    ]
)

角色相关的模板还有各自的专用类：SystemMessagePromptTemplate、HumanMessagePromptTemplate、AIMessagePromptTemplate，本质是预定义了角色的 ChatMessagePromptTemplate 子类，省去手动指定 role 的步骤。此外 PipelinePrompt 支持把一个复杂提示词拆成多个阶段模板顺序组合，前一阶段的输出作为下一阶段的输入变量，用来解决单个超大提示模板难以维护的问题；提示词较大或需要版本管理时，也可以用 load_prompt() 从本地 yaml/json 文件加载。

为什么这些类都能用 | 连接

PromptTemplate、ChatPromptTemplate、聊天模型的继承链最终都汇聚到同一个基类，这是它们能互相拼接成链的根本原因：

PromptTemplate -> StringPromptTemplate -> BasePromptTemplate -> RunnableSerializable -> Runnable
FewShotPromptTemplate -> StringPromptTemplate -> BasePromptTemplate -> RunnableSerializable -> Runnable
ChatPromptTemplate -> BaseChatPromptTemplate -> BasePromptTemplate -> RunnableSerializable -> Runnable

ChatTongyi -> BaseChatModel -> BaseLanguageModel -> RunnableSerializable -> Runnable

Chains 与 LCEL：Runnable 是唯一的入链门槛

LCEL（LangChain Expression Language）是一种声明式写法，用 Python 原生的管道符 | 把多个组件连成可执行流程：chain = prompt | model | parser，上一个组件的输出直接作为下一个组件的输入。能入链的前提只有一个——组件必须是 Runnable 接口的子类（或 callable/mapping 也可以，后面会提到）：

class Runnable(Protocol):
    def invoke(self, input: Any) -> Any: ...       # 单输入单输出
    def batch(self, inputs: List[Any]) -> List[Any]: ...  # 批量处理
    def stream(self, input: Any) -> Iterator[Any]: ...    # 流式输出
    # 还有 ainvoke 等异步方法...

聊天模型、提示词模板、输出解析器、检索器、Agent 等核心组件全部实现了这组方法。prompt | model 这行代码之所以成立，是因为 Runnable 基类重写了 __or__ 运算符：得到的 chain 是一个 RunnableSequence（RunnableSerializable 的子类），继续用 | 追加组件依然会得到 RunnableSequence，这就是链式结构的底层机制。

LCEL 之前：一批已经过时的 Chain 类

LCEL 出现之前，最常见的链类型是 LLMChain（单次问答，无记忆，V1.0 已弃用），以及在它基础上搭出来的一批组合链，现在了解即可，不建议在新代码里用：

  • SimpleSequentialChain / SequentialChain：把多个链顺序连接。前者只支持单一输入输出、隐式用 output 接到下一步的 input；后者支持多变量、需要用 input_variables/output_variables 显式声明每个子链的输入输出关系，能表达更复杂的分支流程（比如按产品名查价格再生成促销文案）。
  • LLMMathChain：把自然语言数学问题转成 Python numexpr 可执行的表达式，再用表达式结果回答问题。
  • RouterChain：根据输入内容自动路由到最匹配的子链（比如按学科分流到不同的问答链），需要配置默认链兜底。
  • StuffDocumentsChain：把多个文档内容整体拼接（"stuff"进单个 prompt）后交给 LLM，适合总结、问答等需要全局理解、但文档数量不多的场景。

这些类现在基本都有 LCEL 版本的替代方案，常见的几个工厂函数：create_sql_query_chain（自然语言转 SQL）、create_stuff_documents_chain（StuffDocumentsChain 的新写法）、create_openai_fn_runnable、create_structured_output_runnable、load_query_constructor_runnable、create_history_aware_retriever、create_retrieval_chain。以 create_sql_query_chain 为例：

from langchain.chains.sql_database.query import create_sql_query_chain
from langchain_community.utilities import SQLDatabase

db = SQLDatabase.from_uri(f"mysql+pymysql://{db_user}:{db_password}@{db_host}:{db_port}/{db_name}")
chain = create_sql_query_chain(llm=llm, db=db)

response = chain.invoke({"question": "查询last_name叫King的基本情况"})
# 限制使用的表：table_names_to_use=["employees"]

RunnableLambda：把普通函数塞进链里

固定功能的解析器不够用时，可以用 RunnableLambda(函数或lambda) 把任意自定义函数包装成 Runnable，插入链中间做数据转换：

from langchain_core.runnables import RunnableLambda

# 把上一步 AIMessage 转成下一步 prompt 需要的字典
my_func = RunnableLambda(lambda ai_msg: {"name": ai_msg.content})

chain = first_prompt | model | my_func | second_prompt | model | str_parser

RunnablePassthrough() 则用于占位透传——原样保留用户输入的全部内容，常见于需要把"原始输入"和"某个中间结果"同时喂给下一步的场景（典型用法在 Retrieval 一节的 RAG 链示例里）。

LCEL 的核心不是"管道符好用"，而是它把提示词、模型、解析器、检索器统一到 Runnable 这一个接口下，链条因此天然支持 invoke/batch/stream 三种调用方式，而不用为每种组合单独维护一套执行逻辑——这也是官方逐步淘汰 LLMChain 这类硬编码链类的原因。

Output Parsers：把自由文本变成结构化数据

输出解析器负责把 LLM 的文本输出转换成程序能直接消费的格式。常用的几种：

解析器输出类型说明
StrOutputParserstr把 AIMessage 转成纯字符串，方便再传给下一个模型（model.invoke 接受字符串，不接受 AIMessage）
JsonOutputParserdict配合 get_format_instructions() 生成格式说明注入提示词，指导模型输出 JSON
XMLOutputParserdict指导模型输出 XML 标签文本，解析后转换成 Python 字典而非保留原始 XML 字符串
CommaSeparatedListOutputParserList[str]把逗号分隔的文本响应转成列表
DatetimeOutputParserdatetime.datetime要求模型按 %Y-%m-%dT%H:%M:%S.%fZ 格式输出，再解析成日期时间对象

进阶的还有 EnumOutputParser（解析为预定义枚举值）、StructuredOutputParser（非结构化文本转结构化字典）、OutputFixingParser（自动修复格式错误的输出）、RetryOutputParser（主解析器失败时调用另一个 LLM 修正后重试）。

一个体现解析器价值的链式例子：第一步生成 JSON 格式的名字，解析后作为字典直接喂给第二个提示词，避免了"上一个模型的输出没处理就传给下一个模型"这种脆弱写法：

str_parser = StrOutputParser()
json_parser = JsonOutputParser()

first_prompt = PromptTemplate.from_template(
    "我邻居姓：{lastname}，刚生了{gender}，请帮忙起名字，"
    "并封装为JSON格式返回给我。要求key是name，value就是你起的名字。"
)
second_prompt = PromptTemplate.from_template(
    "姓名：{name}，请帮我解析含义。"
)

chain = first_prompt | model | json_parser | second_prompt | model | str_parser

Memory：从全量堆消息到实体与知识图谱

模型本身不带记忆，每次调用都是独立的。Memory 组件负责在多轮对话里维护上下文：一个接入了 Memory 的链，每轮交互都会和 Memory 模块交互两次——先读（把历史消息和当前问题拼进提示词）、后写（把新一轮的问答写回 Memory，供下一次读取）。

怎么设计"读"的策略，决定了记忆的几个层次：

层次策略对应组件
1保留完整聊天消息列表，无裁剪无压缩ChatMessageHistory / ConversationBufferMemory
2只返回最近 K 条交互ConversationBufferWindowMemory
3返回过去交互的摘要，而不是原文ConversationSummaryMemory / ConversationSummaryBufferMemory
4只提取和当前相关的实体信息ConversationEntityMemory / ConversationKGMemory

层次 1-2：全量缓冲与滑动窗口

ConversationBufferMemory（笔记标注为 0.3 版本 API）按原始顺序完整存储对话历史，通过 return_messages 控制返回消息对象列表还是拼接字符串；ConversationChain 是它和 LLMChain 的封装，自带默认提示词模板。这类方案的问题很直接：对话一长，内存占用和 token 消耗都线性增长，还会撞上模型的最大输入限制。ConversationBufferWindowMemory 用滑动窗口解决——只保留最近 K 条交互：

from langchain.memory import ConversationBufferWindowMemory

memory = ConversationBufferWindowMemory(k=2)
memory.save_context({"input": "你好"}, {"output": "怎么了"})
memory.save_context({"input": "你是谁"}, {"output": "我是AI助手"})
memory.save_context({"input": "你的生日是哪天？"}, {"output": "我不清楚"})

print(memory.load_memory_variables({}))
# {'history': 'Human: 你是谁\nAI: 我是AI助手\nHuman: 你的生日是哪天？\nAI: 我不清楚'}

ConversationTokenBufferMemory 是同一思路的变体，按 token 数量而不是消息条数截断早期对话。

层次 3-4：摘要、实体与知识图谱

无论按条数还是按 token 截断，都没法同时保证"省内存"和"对话质量"——截断掉的早期信息可能恰好是关键事实。ConversationSummaryMemory 用 LLM 把对话历史压缩成摘要而非保留原文；ConversationSummaryBufferMemory 是混合方案，最近的对话保留原始记录，更早的部分做摘要。再往前一步，ConversationEntityMemory 识别对话中的实体（人名、地点、指标）及其属性，把非结构化对话压缩成结构化字典——在医疗这类高风险场景，这种方式能保证关键事实（如过敏史）被准确保留，而不会被摘要的"自然语言压缩"稀释掉：

同一段问诊对话，ConversationSummaryMemory 产出的是一段自然语言摘要："患者主诉头痛和高血压（140/90），正在服用阿司匹林。患者对青霉素过敏。三天后头痛未缓解，建议更换止痛药。"
ConversationEntityMemory 产出的则是结构化字典：{"症状": "头痛", "血压": "140/90", "当前用药": "阿司匹林（无效）", "过敏药物": "青霉素"}。后者更适合下游做规则校验或强制拦截。

ConversationKGMemory（笔记标注为 V1.0）比实体记忆更进一步：把对话内容转成 (头实体, 关系, 尾实体) 三元组，支持关系推理：

memory = ConversationKGMemory(llm=llm)
memory.save_context({"input": "向山姆问好"}, {"output": "山姆是谁"})
memory.save_context({"input": "山姆是我的朋友"}, {"output": "好的"})

memory.get_knowledge_triplets("她最喜欢的颜色是红色")
# [KnowledgeTriple(subject='山姆', predicate='是', object_='我的朋友'),
#  KnowledgeTriple(subject='山姆', predicate='最喜欢的颜色是', object_='红色')]

此外还有 VectorStoreRetrieverMemory：把对话历史存进向量数据库，按语义相似度检索最相关的 k 条历史。它和 RAG 的区别在于检索目标不同——RAG 检索的是与问题最相关的外部知识，VectorStoreRetrieverMemory 检索的是与当前问题最相关的历史对话记录。

V1.0 的记忆实现：RunnableWithMessageHistory

上面这批 Conversation*Memory 类多数来自较早版本；LangChain 1.0 把短期记忆统一到 RunnableWithMessageHistory 上——它给已有的链包一层，自动完成"读历史 → 拼提示词 → 调模型 → 写回历史"，底层的存储后端通过一个 get_history(session_id) 函数按需返回：

from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_core.chat_history import InMemoryChatMessageHistory

store = {}  # key是session_id，value是InMemoryChatMessageHistory对象
def get_history(session_id):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

conversation_chain = RunnableWithMessageHistory(
    base_chain,
    get_history,
    input_messages_key="input",
    history_messages_key="chat_history"
)

session_config = {"configurable": {"session_id": "user_001"}}
res = conversation_chain.invoke({"input": "总共有几个宠物"}, session_config)

InMemoryChatMessageHistory 只是内存存储，程序退出就丢；要做长期记忆，只需继承 BaseChatMessageHistory，实现 add_messages、messages（用 @property 装饰，保持和基类同名属性而非方法的接口一致）、clear 三个方法，把消息序列化后写文件或写数据库：

自定义长期记忆：FileChatMessageHistory

class FileChatMessageHistory(BaseChatMessageHistory):
    def __init__(self, session_id, storage_path):
        self.session_id = session_id
        self.storage_path = storage_path
        self.file_path = os.path.join(self.storage_path, self.session_id)
        os.makedirs(os.path.dirname(self.file_path), exist_ok=True)

    def add_messages(self, messages: Sequence[BaseMessage]) -> None:
        all_messages = list(self.messages)
        all_messages.extend(messages)
        new_messages = [message_to_dict(m) for m in all_messages]
        with open(self.file_path, "w", encoding="utf-8") as f:
            json.dump(new_messages, f)

    @property
    def messages(self) -> list[BaseMessage]:
        try:
            with open(self.file_path, "r", encoding="utf-8") as f:
                return messages_from_dict(json.load(f))
        except FileNotFoundError:
            return []

    def clear(self) -> None:
        with open(self.file_path, "w", encoding="utf-8") as f:
            json.dump([], f)

这里的 message_to_dict/messages_from_dict 是 LangChain 提供的消息对象和字典之间的互转函数，AIMessage/HumanMessage/SystemMessage 都是 BaseMessage 的子类，序列化思路对接任何存储后端都适用（文件只是最简单的一种）。

Retrieval：LangChain 怎么组织检索的六个环节

专有领域的问答场景下，LLM 缺乏专业知识细节，容易产生"幻觉"。Retrieval 相关组件解决的是"怎么把外部知识接进来"这个工程问题，LangChain 把它拆成六个环节：Source → Load → Transform → Embed → Store → Retrieve。这里只讲 LangChain 框架怎么组织这些组件，检索效果的评估和调优不在这篇的范围内。

Load：文档加载器

文档加载器把不同来源的非结构化数据统一读成 Document 对象，都实现了 load()（一次性加载全部）和 lazy_load()（延迟流式加载，避免大文件内存溢出）两个接口：

加载器依赖/关键参数说明
CSVLoader-按行读取，逐行转为 Document
JSONLoader依赖 jq 库通过 jq_schema 语法抽取字段；text_content/json_lines 控制解析方式
TextLoader-整个文本文件读成一个 Document
PyPDFLoader依赖 pypdfmode="page" 逐页生成 Document，mode="single" 整篇合并；支持 password
UnstructuredHTMLLoader / UnstructuredMarkdownLoader依赖 unstructuredstrategy 可选 fast/hi_res/ocr_only；mode="elements" 按标题、段落、表格等语义元素拆成多个小文档
DirectoryLoader-批量加载一个文件夹，glob 过滤文件类型，loader_cls 指定具体加载器，支持多线程

Transform：文本拆分器

拿到 Document 之后直接整体丢给模型有两个问题：一是无关信息太多会稀释模型的注意力，二是大文档超出模型的最大输入长度。拆分策略从简单到复杂：按句子切、按固定字符数切、固定字符数加重叠窗口、递归字符切分（最常用）、按语义内容切分。所有 TextSplitter 共享一组参数——chunk_size（块的最大字符数）、chunk_overlap（相邻块的重叠字符数，通常取 chunk_size 的 10%-20%）、length_function（默认 len）——以及三个调用方法：

split_text(str) -> List[str]                    # 最基础的分割
create_documents(List[str]) -> List[Document]     # 内部调用 split_text
split_documents(List[Document]) -> List[Document] # 内部调用 create_documents
切分器切分依据备注
CharacterTextSplitter单一分隔符 + chunk_size指定了 separator 时优先在分隔符处切，避免句子被硬切断；若 chunk_size 小于片段本身，overlap 会失效
RecursiveCharacterTextSplitter递归尝试 ["\n\n", "\n", " ", ""]最通用的拆分器，优先保留自然语言边界，同时逼近目标 chunk_size
TokenTextSplitterToken 数量（如 encoding_name="cl100k_base"）严格按 token 计数分割，同时尽量在自然边界处切断
SemanticChunker语义相似度按语义结构而非固定大小分块，块内语义更完整
HTMLHeaderTextSplitter<h1>/<h2> 等标题标签按 HTML 标题层级分块，保留层级结构信息
CodeTextSplitter编程语言语法结构支持 cpp/go/java/js/python 等语言，避免在函数或类中间截断
MarkdownTextSplitterh1/h2/h3 等标题按 Markdown 标题层级分割

Embed 与 Store：向量化与向量数据库

嵌入模型对外暴露两个接口：embed_documents(texts) 用于批量文档向量化，embed_query(text) 用于单个查询向量化。向量数据库组件（如 Chroma）接收 Document 列表和嵌入模型，自动完成向量化并写入：

my_embedding = OpenAIEmbeddings(model="text-embedding-ada-002")
docs = text_splitter.split_documents(documents)
db = Chroma.from_documents(docs, my_embedding)

query = "人工智能的核心技术都有啥？"
docs = db.similarity_search(query)
# Chroma 有内存模式和持久化模式：指定 persist_directory 才会落盘

检索背后的打分方式有三种：similarity_search_with_score 用 L2 欧式距离，分数越小越相似（L2 = sqrt(Σ(x_i - y_i)²)，取值范围 [0, +∞)）；_similarity_search_with_relevance_scores 用余弦相似度，分数越接近 1 越相似；max_marginal_relevance_search（MMR）在相关性和多样性之间做平衡，lambda_mult 取值 0-1，越接近 0 多样性越高、越接近 1 相关性权重越高，默认 0.5，用来避免返回结果高度同质化。

Retrieve：检索器与组装成链

向量存储对象本身不是 Runnable，不能直接入链，需要通过 as_retriever() 转成检索器：

retriever = db.as_retriever(search_kwargs={"k": 4})

retriever = db.as_retriever(
    search_type="similarity_score_threshold",  # 只有相似度超过阈值才召回
    search_kwargs={"score_threshold": 0.1}
)

retriever = db.as_retriever(search_type="mmr", search_kwargs={"fetch_k": 2})

检索器输入用户提问（str），输出 list[Document]；配合 RunnablePassthrough() 透传原始输入，就能把"用户问题"和"检索结果"同时组装进最终的 prompt，拼成一条完整的 RAG 链：

retriever = vector_store.as_retriever(search_kwargs={"k": 2})

prompt = ChatPromptTemplate.from_messages(
    [
        ("system", "以我提供的已知参考资料为主，简洁和专业的回答用户问题。参考资料:{context}。"),
        ("user", "用户提问：{input}")
    ]
)

def format_func(docs: list[Document]):
    if not docs:
        return "无相关参考资料"
    return "[" + "".join(doc.page_content for doc in docs) + "]"

chain = (
    {"input": RunnablePassthrough(), "context": retriever | format_func}
    | prompt | model | StrOutputParser()
)
res = chain.invoke("怎么减肥？")
六个环节各自解耦：Load 只关心"怎么读进来"，Transform 只关心"怎么切得合理"，Embed/Store 只关心"怎么变成可检索的向量"，Retrieve 只关心"怎么找出相关片段"。LangChain 的价值在于给每个环节都定义了统一接口，替换某一环（比如换一个 Embedding 模型或换一种切分策略）不需要动其余部分的代码。

Tools 与 Agent：让 LLM 具备行动能力

Tool 本质是封装了特定功能的可调用模块，让 LLM 突破纯文本生成的限制，去调用搜索、计算、数据库查询等外部能力。一个 Tool 通常包含 name（唯一标识）、description（LLM 据此判断何时调用）、输入的 JSON Schema、要执行的函数、return_direct（是否跳过后续推理直接把工具结果返回给用户）。定义方式最简单的是 @tool 装饰器，默认用函数名做工具名、文档字符串做描述：

from langchain.tools import tool
from pydantic import BaseModel, Field

class FieldInfo(BaseModel):
    a: int = Field(description="第1个参数")
    b: int = Field(description="第2个参数")

@tool(name_or_callable="add_two_number",
      description="two number add", args_schema=FieldInfo, return_direct=True)
def add_number(a: int, b: int) -> int:
    """两个整数相加"""
    return a + b

需要更精细控制同步/异步实现时用 StructuredTool.from_function，第三方工具接入通常也走这条路径。模型决定调用工具时，返回的 AIMessage 里 content 通常为空、工具调用信息装在 additional_kwargs 里；模型判断不需要工具时，直接返回自然语言 content。

Agent 的两种模式

没有 Agent 时，LLM 只能基于训练数据回答问题，遇到需要实时数据或复杂工具调用的场景就会卡壳。Agent 让 LLM 按"思考任务 → 选择工具 → 执行调用 → 根据结果调整策略"的循环自主运行，和 Chain 的区别在于：Chain 的执行顺序在开发时就已经固定，Agent 的下一步由 LLM 在运行时动态决定。

模式输出形式特点
Function Calling结构化 JSON直接生成工具调用参数，效率更高，适合工具边界明确的场景
ReAct（Reasoning + Acting）自由文本用自然语言描述"推理→行动"的链式思考过程，具备反思和自我纠错能力，响应延迟更高；LangChain 的 Agent 默认按这种模式运行
 
from langchain.agents import create_agent
from langchain_core.tools import tool

@tool(description="获取股价，传入股票名称，返回字符串信息")
def get_price(name: str) -> str:
    return f"股票{name}的价格是20元"

agent = create_agent(
    model=ChatTongyi(model="qwen3-max"),
    tools=[get_price],
    system_prompt="你是一个智能助手，可以回答股票相关问题。"
)

res = agent.invoke({"messages": [{"role": "user", "content": "传智教育股价多少"}]})

Agent 还支持一套中间件（middleware）机制，通过节点式钩子（before_agent/after_agent/before_model/after_model）和包装式钩子（wrap_model_call/wrap_tool_call）拦截执行过程的各个阶段，加日志、做重试、切换提示词（dynamic_prompt）都靠它。这里只是提一下机制存在，更完整的多步规划、状态管理和多智能体编排放在 LangGraph 相关的笔记里单独展开，不在这篇重复。

LangSmith：可观测性怎么落地

LangSmith 是专门针对 LangChain 应用做测试、监控和分析的平台，和 LangChain 无缝集成，用来支撑从原型阶段到生产阶段的过渡。它主要提供六类功能：Debugging（调试）、Playground（沙盒）、Prompt Management（提示管理）、Annotation（注释）、Testing（测试）、Monitoring（监控）。

其中 Filters（条件过滤）是定位问题时最直接会用到的功能：面对一次运行或一整条 chain 的执行记录，需要快速定位到关注的片段或者需要调试的错误，LangSmith 提供三种过滤方式：

  • 点击 Filters 面板的按钮，手动添加过滤条件；
  • 用自然语言描述想要查询的目标（AI query），LangSmith 会把描述自动转换成对应的过滤器；
  • 直接勾选右侧的 filter shortcuts，快速筛选出需要的信息。

三种方式本质是同一套过滤能力的不同入口：手动配置最精确，AI query 上手成本最低，shortcuts 适合重复性高的排查场景。
