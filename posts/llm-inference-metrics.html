LLM 推理性能与并发指标：TTFT、TPOT、QPS 与 TPS

延迟决定交互体验，Token 吞吐反映处理能力，并发数描述系统中的在途请求。把它们放到同一套输入输出长度、统计边界和服务目标下，才能判断推理系统的瓶颈与可用容量。

LLM推理 性能优化 并发压测 vLLM

先统一请求生命周期和测量时钟

LLM 请求通常经历网络传输、准入或排队、Prefill（预填充）、Decode（解码）与流式传输。长输入主要增加 Prefill 的计算量，长输出会占用更多解码步数；在高负载下，排队和调度也会成为主要延迟来源。只看请求总耗时或 QPS，很难判断这些成本来自哪里。

以下以客户端接收输出 Token 的时钟为例：t₀ 是请求发出时间，t₁ 是第一个输出 Token 到达时间，tₙ 是最后一个输出 Token 到达时间，N 是输出 Token 数。服务端也可以记录同类指标，但应明确起止点，并与客户端时钟分别报告。

Token 数以模型的分词口径计，不等于字数。流式接口的一次数据块可能含多个 Token，首个控制消息也可能没有文本；直接把数据块间隔当作逐 Token 延迟，会改变指标含义。

TTFT · TPOT · ITL · 吞吐与限流 · 并发与容量 · SLO压测

TTFT：第一个输出 Token 多久到达

TTFT（Time To First Token）是从请求发出到收到第一个输出 Token 的时间，刻画用户等待系统开始回答的体验。

TTFT = t₁ − t₀
客户端口径通常包含网络、排队、Prefill、首 Token 采样与发送。服务端若从开始执行计时，会排除其中一部分，比较时必须使用相同边界。

输入长度是重要因素，但不能把 TTFT 全部归因于 Prefill。相同 Prompt 在排队、缓存命中、批处理策略和硬件配置不同时，首 Token 延迟可能明显不同。

优化方向

  • 用请求追踪区分网络、队列与模型执行时间，先定位占比最大的部分。
  • 压缩无用输入，评估前缀缓存、Prefill 调度和推理后端的收益，同时记录缓存命中条件。
  • 调整准入和批处理策略，结合硬件并行能力评估；不能仅凭单请求测试判断高负载体验。

TPOT：首 Token 之后的平均生成时间

TPOT（Time Per Output Token）描述首 Token 之后，每个输出 Token 的平均耗时。若端到端延迟取到最后一个输出 Token，则：

TPOT = (tₙ − t₁) / (N − 1) = (E2E − TTFT) / (N − 1)
E2E = tₙ − t₀，且 N ≥ 2。输出仅有一个 Token 时，TPOT 没有可用的后续间隔，不应强行记为零。

假设示例：首 Token 在0.2秒到达，第50个 Token 在2.65秒到达，则 TPOT = (2.65 − 0.2) / 49 = 50ms。

TPOT 会随模型大小、上下文增长、内存带宽、KV Cache、批内竞争和调度变化，并非常量。对于较长输出，单请求平均解码速率约为 1 / TPOT；它与整个服务的聚合 Output TPS 是不同口径。

优化方向

  • 评估量化、KV Cache 管理、高效注意力实现与推理后端，并同时检查质量和硬件适配。
  • 改善 CPU-GPU 同步及内存访问，区分解码计算与传输造成的等待。
  • 用连续批处理提高资源利用率，但同步观察单请求 TPOT 和尾延迟，避免只汇报总吞吐。

ITL：相邻 Token 的实际间隔

ITL（Inter-Token Latency）是连续两个输出 Token 到达的时间差。它是一组间隔，而不是单个平均值，可以用分布观察流式输出是否出现停顿。

ITLᵢ = tᵢ − tᵢ₋₁，i = 2, …, N
同一请求、同一时钟且有逐 Token 时间戳时，TPOT = 平均(ITL₂, …, ITLₙ)。若只能获得流式数据块时间戳，应标为块间延迟，不能声称测得了严格逐 Token ITL。

假设示例：三个相邻间隔分别是40ms、60ms和50ms，平均为50ms；平均值相同的另一段输出，仍可能包含很长的停顿。因此需要同时报告 ITL 的分位数或停顿比例。

指标回答的问题常见观察重点
TTFT多久开始回答排队、Prefill、前缀缓存与传输
TPOT平均生成多快解码计算、带宽、KV Cache与批处理竞争
ITL分布生成是否平稳调度抖动、资源竞争、同步及流式传输
E2E = TTFT + (N − 1) × TPOT
此式沿用首个/最后一个输出 Token 的时间戳。若“请求完成”还包含流关闭、后处理等额外时间，应另计该开销，不能换用结束时钟后仍直接套用此式。

QPS、TPS与RPM/TPM：请求量、Token量和配额

两个请求的输入输出长度可能相差几个数量级。例如在稳定负载下，假设每秒完成2个请求、每个平均生成2000个 Token，聚合输出量约为4000 Token/s。相同 QPS 下，短回答服务与长文本服务对解码资源的要求并不相同。

指标定义 / 用途报告时需明确
QPS / RPS单位时间的查询 / 请求数量到达、准入、完成或成功请求分别计数；完成QPS = 窗口内完成数 / 窗口秒数。
Input TPS每秒处理的输入Token量逻辑输入数与实际执行Prefill的Token数可能因缓存而不同。
Output TPS每秒产生的输出Token总量是服务聚合吞吐；不等于单个用户看到的Token/s。
RPM / TPM每分钟请求数 / Token数，常用于API配额TPM包含哪些Token、滑动窗口及预留计费规则以提供方说明为准。
Concurrency同一时刻系统中的请求或序列数在途、排队、运行、框架序列数与准入上限是不同边界。

云API的配额由模型、账户和服务策略决定，不能把某一档的限额当作长期通用配置。RPM/TPM限制也不是GPU容量：即使服务器有空闲算力，请求仍可能先触发配额；反过来，配额允许通过的流量也不保证满足延迟目标。

“并发80”究竟约束了哪一层

“支持80并发”必须附带统计位置和工作负载。它可能是客户端同时发起的在途请求数、网关允许进入的请求上限，也可能是推理调度器的序列限制；不能直接解释为80个请求都在同一时刻执行 Decode。

  • 客户端或网关：在途数可能同时包含排队和运行请求。超过准入阈值后，是排队、拒绝还是返回429，取决于实际策略。
  • 推理框架：max_num_seqs等参数约束调度中的序列数量，具体含义需按框架和版本核对；Prefill/Decode混合、Token预算及采样方式都会影响实际批次，配置值不等于恒定活跃用户数。
  • 显存与KV Cache：可容纳数量随输入长度、已生成长度、模型层数、KV精度和并行方式变化。不能只用GPU总显存除以一个固定“每请求显存”承诺容量。

用Little's Law连接平均并发、吞吐与耗时

L = λ × W
L：同一系统边界内的平均在途数量；λ：稳定时间窗内的平均流入/流出率；W：请求在该边界内的平均停留时间。若L包含队列，W也必须包含排队时间。

假设示例：系统稳定且平均在途数为80、平均停留时间为5秒，则 λ = 80 / 5 = 16请求/秒；平均停留20秒时则为4请求/秒。这描述的是对应负载下的平均关系，不能把“并发上限80”直接换算成保证可达的16 QPS。

持续增压导致队列增长时，流入率可能大于完成率，短窗口内直接套用稳态关系会误导。成功QPS若排除了失败和取消请求，也不能直接代替覆盖全部请求的λ；数量、时间和流量必须使用同一统计边界。

按工作负载与SLO确定可用容量

并发拐点需要测量，但吞吐最大点不一定是业务可接受点。应该寻找质量、成功率和延迟约束同时满足时的最大稳定吞吐。

  1. 固定并描述负载。记录模型/精度、硬件、输入输出Token分布、缓存命中、流式方式及采样设置；长上下文和长输出专项单独测试，不能只汇报平均长度。
  2. 定义服务目标。按业务设定TTFT、TPOT、端到端延迟的分位数目标及成功率；若举例设置TTFT P95<1.5s、TPOT P95<50ms，这只是目标示例，不是所有业务通用的体验阈值。
  3. 逐步增加压力。分别用固定在途并发和受控到达率模拟负载；先预热，再在稳定窗口记录准入/完成/成功QPS、Input/Output TPS、队列长度、超时及拒绝率。
  4. 观察拐点和恢复。当吞吐不再增长、TTFT尾延迟陡升或队列持续堆积时，已接近瓶颈；结合SLO选择更早的可用点，并验证突发流量和降压后的恢复。

评估准入控制、连续批处理、前缀缓存或后端优化时，保持对照负载一致。吞吐上涨若来自更多超时、截短输出或质量退化，需要单独披露这些变化。

测量工具与报告清单

  • 服务指标：结合推理框架metrics、队列与Token计数器；指标名和定义以实际部署版本为准。
  • 请求追踪：记录发出、准入、开始计算、首Token、末Token和终止状态，区分客户端与服务端时钟；用PyTorch Profiler等工具定位执行瓶颈。
  • 压测：使用Locust、k6或支持流式LLM测量的工具；确保客户端没有成为发送或接收瓶颈，按预热和稳定窗口分别统计。
  • 汇总：同时给出工作负载、平均/峰值在途数、完成与成功QPS、聚合TPS、TTFT/TPOT分位数、ITL停顿及失败率；说明请求等权和Token间隔等权的聚合差异。
TTFT回答“什么时候开始”，TPOT与ITL回答“如何持续输出”，QPS/TPS回答“整体处理多少”，并发与队列说明“系统里积压多少”。只有把这些指标与Token长度、统计边界和SLO一起报告，“支持多少并发”才是可解释、可比较的结论。
