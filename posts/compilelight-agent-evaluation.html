1成功的定义：四档分级

一个 Agent 给出了答案，是真的做对了，还是瞎蒙的？还有一种情况是它做了一半，但诚实地说"我查不到了"——这两种能算同一种"成功"吗？如果只报一个笼统的成功率数字，很容易让人怀疑指标口径有问题。

可以用完整完成、部分完成、正确失败、错误失败四档描述任务结果。业务成功与安全合规要分别标注：通过编译门禁不等于答案正确，正确拦截也不自动计为业务成功。

  • 完整完成：所需子目标全部完成，答案或工具结果通过任务级核验。
  • 部分完成：明确报告尚未覆盖的子目标，并保留已验证的结果。
  • 正确失败：因权限、预算或证据不足而中止，输出可检查的原因。
  • 错误失败：任务结果错误、证据不足却继续输出，或发生门禁绕过。

CompileLight 最新业务材料使用“成功率”78.2%→89.4%。材料没有给出四档的逐项数量，不能据此推定它等于完整完成率或包含部分完成；设计自己的评估时，应先固定成功分母和计分规则。

2为什么用回放评估，而非直接线上 A/B

拿历史流量回放，就像拿去年的考卷让今年的考生做——考卷一样，但考生变了（模型更新）、考场变了（工具版本变了）、题型也可能变了（用户意图分布变了）。回放结果凭什么能代表线上表现？

CompileLight 最新成果来自10,284次业务流量回放。回放便于对比同类请求，并检查门禁、工具行为与执行证据，但是否代表生产表现取决于流量窗口、意图分布及环境保真度。

  1. 冻结环境：记录模型、Prompt、工具、Contract和资产Snapshot版本。
  2. 隔离副作用：用沙箱或受控回放结果替代真实写入；不能通过重放制造新的业务操作。
  3. 比较分布：按意图、路由、风险和长尾任务分层；分别报告自然流量与额外边界用例。

模型分析与Blueprint提案可能调用LLM。应区分确定性Compiler的回放一致性与模型输出的波动，不把整条控制链路称为确定性代码。

3命中率会不会是"假命中"

缓存命中率高，但如果用户问的是 A，缓存里存的是 B，因为 A 和 B 在向量空间里离得近就直接返回 B 的结果——这种"假命中"用户当场可能看不出来，后果却是灾难性的。

命中率高不等于复用正确。至少同时记录候选命中率、经过验证的有效复用率和错误复用率，并固定各自分母。

  1. 实体与输入对齐：检查当前请求的关键实体、参数和上下文，避免相似问法复用了不同对象的结果。
  2. Contract与版本检查：匹配前置条件、Scope、资产状态和Snapshot，执行前重新经过门禁。
  3. 抽样核验：审核被接受和被拒绝的候选，分别观察误复用与漏复用；按业务域调阈值。

阈值需从有标注的数据中确定，不把某个相似度值或旧缓存命中百分比推广为通用标准。

4编译门禁的有效性：拦截率与误杀率的平衡

LLM 提议什么操作，要经过 Schema、权限、风险、预算四道门禁才能执行。门禁太严，Agent 什么都干不了；太松，又拦不住越权——松紧刚好怎么判断？

Schema / Scope / Risk / Budget 门禁负责确定性批准。评估应同时观察拦截率、误拦截与漏放，单独一个“通过率”无法说明安全性。

  • 拦截率：被拦截提议数÷全部提议数，说明门禁触发频率。
  • 误拦截：被拦截提议中，人工复核判定应放行的比例。
  • 漏放：被批准提议中，事后核验判定应拦截的比例。

抽检应覆盖放行与拒绝两组，并记录样本量。被拦截后可中止、重新提案或转人工审核；审核后的修改仍要重新编译，不能绕过原门禁。

5路由决策质量：REUSE/HYBRID/NEW 选对了吗

三个模式里，如果该用 NEW 的时候错用了 REUSE，把旧结果硬套到新问题上，用户拿到的是"看起来合理但其实是错的"答案。

路由首先是资产覆盖决策：REUSE覆盖全部所需步骤，HYBRID只求解剩余缺口，NEW处理覆盖不足的任务并可保留已有资产步骤。

  • 事前：用Contract、资产版本、依赖与权限核对复用条件，不能仅凭缓存相似度决定REUSE。
  • 事中：检查复用步骤与缺口产物的输入输出是否衔接，验证失败时不得强行接入。
  • 事后：在人工标注样本上构建三模式混淆矩阵，分别统计过度探索和错误复用。

漏复用主要增加开销，错误复用可能影响结果与安全；两类错误应分别报告。REUSE减少已知执行步骤的额外决策Token，不代表整个请求零Token。

6如何核验越权与重复副作用

"我检查了，没问题"不能算数，需要一套可重复、可验证的审计机制，让第三方也能确认"这个 Agent 确实没越权"。

验证越权与重复副作用，需要把门禁决策、实际工具调用、资源Scope、幂等标识和返回证据关联起来。Ledger提供执行证据，不能仅凭日志存在就推断它不可篡改。

  1. 权限核验：把实际调用对象与该次请求获批的Scope对照，并检查权限配置本身。
  2. 副作用核验：在适用操作上检查幂等键、重试和补偿，确认没有重复提交。
  3. 受控回放：固定版本、隔离外部写入，比较门禁决定和调用序列。

“本次样本未观察到违规”与“系统永远不会违规”是不同结论。审计结果必须注明检查范围、时间和样本量。

7资产索引与资产健康度

资产沉淀了很多，但如果检索不到，Agent 就会白白走 NEW 模式浪费成本；沉淀了但从没被复用的资产，就是占索引空间、增加检索噪声的"僵尸资产"。

分别评估Header召回、Contract匹配和资产复用后的结果，才能判断问题发生在检索、匹配还是资产内容。

  • Header召回率：有可用资产的标注任务中，检索找到了对应候选的比例。
  • Contract精确率：判定可复用的候选中，经核验确实可复用的比例。
  • 资产利用率与复用成功率：分别衡量资产是否被使用，以及使用后任务是否完成。

按五类资产与业务域分别看结果。过严Contract和低质Body需要不同修复；Ledger中的经验经审核、验证与版本发布后才进入Registry，不实时修改当前运行的Snapshot。

8Token 节省是不是拿质量换来的

如果基线花 100 Token 做对了 95 个任务，优化后花 25 Token 只做对了 60 个任务，这省 Token 有什么意义？Token 节省必须和任务质量捆绑报告，否则就是数字游戏。

最新业务版对比ReAct：10,284次回放中，成功率78.2%→89.4%（+11.2个百分点），同时节省74.8% Token。

成果图将ReAct Token开销归一化为100，CompileLight为25.2；这是相对指数，不是每个请求只用25.2个Token。

资产复用、语义缓存和固定执行器可减少重复规划与执行中的额外决策，但现有素材没有各组件的单独消融。不能把整体节省拆成未经核验的归因百分比，也不能把REUSE解释为所有分析、对齐和提案都不调用模型。

9受控探索：区分"真推理"与"碰巧对"

Agent 在不确定时会在受控白名单内深度探索。探索出的结论是真的推理出来的，还是试来试去碰巧对了？如果是碰巧，下次遇到类似问题它还会翻车。

有界System 2按冻结上下文、缺口分类、受限求解与输出验证组织流程。工具调用是允许的分支，不必在每次求解中出现。

  1. 扰动测试：改变非关键上下文与证据顺序，检查结果稳定性；稳定只是鲁棒性信号，不能单独证明推理正确。
  2. 证据核验：逐项检查输出是否被材料或工具结果支持，验证类型、前置条件和约束。
  3. 泛化测试：在不同请求上检验候选经验，再决定是否转成可复用资产。

分别报告质量、预算超限、中止原因和工具违规；最终答案碰巧正确不应掩盖流程问题。

10LLM-as-Judge 用在哪、局限在哪

LLM 当裁判有个毛病：只看最终输出，看不到 Agent 中间那几十步是怎么走的。一个 Agent 中间乱调了十几次工具，最后碰对了，LLM 裁判只看到对的答案，给了高分——这公平吗？

确定性规则适合检查Schema、权限、预算和可核验工具结果；LLM-as-Judge可辅助判断语义质量、证据充分性与失败类型。任务是否完成仍需要任务级标准，不能仅由编译通过或语言流畅判定。

  • 向Judge提供必要的执行证据，避免只看最终回答。
  • 采用盲评与顺序交换，检查位置偏差、模型偏好和长尾场景偏差。
  • 与人工标注对照，并把Judge分数作为单独信号记录。

这是一套可采用的评估设计，当前成果素材没有给出该Judge流程的独立实验结果。

11评估集怎么构建：分层 + 真实流量混合

如果评估集里全是正常情况，那 Agent 在边界场景下会不会崩，根本无从得知。评估集的质量决定了评估结论的可信度。

自然流量层与诊断用例层承担不同目的，应分别统计，避免人为添加大量困难样本后仍称结果代表线上自然分布。

  • 自然流量：按约定窗口采样，保留意图、路由和风险分布。
  • 边界用例：覆盖工具失败、权限不足、Contract不匹配与预算耗尽。
  • 对抗用例：覆盖越权诱导、重复提交、错误资产复用和未经验证产物。

CompileLight最新素材给出回放总数10,284，没有提供三层精确占比或样本构建历史；这里不据总量补写这些数字。

12从零设计评估方案，最先回答三个问题

重新做一遍这个项目的评估设计，不可能一口气把什么都测了。哪三个问题回答不好，后面的评估就都是空中楼阁？

  1. 什么算完成：明确任务级成功条件、部分完成和正确中止的计分方式。
  2. 在哪里测：区分离线回放、影子流量和受控线上实验，记录版本及流量窗口。
  3. 失败如何分类：记录检索遗漏、Contract不匹配、编译拒绝、工具异常、结果错误和预算耗尽。

这些约定决定分母、对照条件和后续归因，应在评测开始前固定。

13整体延迟与分组口径

整体端到端延迟、缓存分组延迟和内部阶段耗时各在测什么？先固定计时范围与样本分组，才能判断尾部延迟改善来自哪里。

采用最新业务版整体端到端口径：ReAct P95 103.64s，CompileLight 54.2s，相对降低47.7%。

整体P95从全体请求的总耗时分布计算。缓存命中组、未命中组或某个内部阶段的P95不能直接替代它；各阶段P95也不能相加得到端到端P95。

  • 固定计时起止点，记录失败、重试和超时的处理规则。
  • 给每条请求关联阶段耗时与路由，分别汇报整体和分组分布。
  • 同时观察P50/P95/P99与样本量，分析工具调用、排队和推理的尾部开销。

旧缓存延迟没有足够信息与整体指标对齐，本次不作为成果展示，也不据此推导延迟下降。

14执行视图冻结怎么验证

"冻结"是个承诺，怎么证明它真的冻住了？如果执行到一半底层资产版本变了，Agent 还在用旧版本，但用户以为用的是新版本——这就出事了。

Snapshot绑定本次运行使用的资产版本，Blueprint作为请求状态数据由固定执行器消费。需要检查从计划批准到结果输出是否一直使用这些绑定版本。

  • 运行前：记录Snapshot与资产绑定，核验Blueprint依赖和版本。
  • 运行中：用故障注入验证外部资产更新不会改变已获批计划的含义。
  • 运行后：对照Ledger与绑定版本，检查重试或恢复是否引入漂移。

缺口求解产生的类型化产物与未来Registry资产要分开管理：前者经验证供本次执行消费，后者经过审核与发布后供未来运行使用。

15硬过滤的精度与召回权衡

硬过滤直接砍掉不合格的候选，判断标准是死的，但现实是活的。砍错了一个，后面的步骤就全白费了。

检索前硬过滤与Compiler最终批准承担不同职责。确定性过滤可基于版本、Scope和Schema等条件缩小候选范围，最终计划仍须经过完整编译门禁。

  • 过滤精度：被过滤候选中，人工复核确认应排除的比例。
  • 过滤召回：所有应排除的候选中，实际被过滤的比例。
  • 业务影响：过滤后的资产覆盖、路由和任务成功是否改善。

用误过滤案例修订规则，避免仅以候选减少量判断收益。权限等必须约束不能为了提高召回而绕过。

16这套评估体系的局限性

没有一套评估体系是完美无缺的。清楚自己这套评估的边界在哪、哪里可能出问题、如果资源更多会怎么改进，本身就是评估能力的一部分。

  1. 回放代表性：历史请求不能覆盖所有未来意图与外部工具变化，需持续收集新失败类型。
  2. 统计不确定性：最新素材提供总量与聚合结果，未提供逐样本数据、置信区间或组件消融；不由聚合收益推断每个组件的独立作用。
  3. 版本边界：公开轻量版展示SQLite/FTS5/NumPy/Ollama等实现，业务回放成果来自业务版；不能把两者拼成同一次复测。
如果有更多资源，下一步最想做的是构建一个自动化的评估集迭代管线——每次发现新的失败模式，自动构造对应的评估用例加入边界层，让评估集跟随系统的演化而演化，而不是依赖人工手工构造。
