训练范式与基础模型特征

大模型的训练整体上分三个阶段：预训练、SFT（监督微调）、RLHF（基于人类反馈的强化学习）。LLM是NLP中的重要组成部分，本质是预测自然语言文本中下一个词或字符的概率分布，可以看作是对语言规律的学习和抽象。基于Transformer架构的模型通过大规模无监督学习来学习语言规律和上下文信息，再在微调阶段做有监督学习和优化，从而生成连贯、有意义的文本——预训练阶段常用掩码语言模型或下一句预测等技术，微调阶段则针对具体任务优化。

基础模型的四个特征

  • 规模和参数量大：通过从数亿到数千亿级别的参数捕获复杂的数据模式，从而理解和生成极其丰富的信息
  • 广泛数据集的预训练：使用大量多样化数据预训练，学习语言、图像等数据的通用特征表示
  • 适应性和灵活性强：能通过微调（fine-tune）或少样本学习高效迁移到各种下游任务，具备很强的跨域能力
  • 计算资源需求大：巨大的模型规模带来高昂的数据存储、训练时间、能量消耗和硬件成本

从LLM到Agent：为什么需要记忆、工具与规划

大语言模型可以接受输入、分析推理、输出文字/代码/媒体，但无法像人类一样拥有规划思考能力、运用工具与物理世界互动、以及拥有长期记忆能力。AI Agent是基于LLM的、能够自主理解、自主规划决策、执行复杂任务的智能体，设计目的是处理那些简单语言模型无法直接解决的问题——尤其是任务涉及多个步骤或需要外部数据源的情况。可以简单概括为：

LLM = 接受输入、思考、输出。
人类 = LLM（接受输入、思考、输出）+ 记忆 + 工具 + 规划 → Agent

以智能家居为例：用户说"我觉得有点冷"，系统感知到温度诉求后规划出"检查当前温度 → 决定升高几度 → 调整并反馈"的步骤，执行后再观察用户反馈决定是否继续调整——这个感知、规划、行动、观察的循环，就是Agent决策流程的雏形。要让LLM具备这样的能力，核心要补齐四个模块：规划（Planning）、记忆（Memory）、工具使用（Tools）、执行（Action）。

智能体的四大能力：规划、反思、记忆与工具

规划，可以理解为"观察和思考"。类比人类接到任务时的思维模式：先想清楚怎么完成，再审视手头的工具、思考如何高效使用，然后把任务拆成子任务，执行过程中不断反思和完善，同时判断任务何时可以终止。让LLM具备这套思维模式，最重要的是解决两个问题：怎么把任务拆成子任务，以及怎么在执行中反思改进。

子任务分解：思维链与思维树

思维链（Chain of Thoughts, CoT）已经是一种比较标准的提示技术：要求LLM「think step by step」，模型会把问题拆解成多个步骤，一步步思考和解决，使输出结果更加准确——这是一种线性的思维方式。

思维树（Tree-of-Thought, ToT）是对CoT的进一步扩展：在思维链的每一步推理出多个分支，拓扑展开成一棵思维树，用启发式方法评估每个推理分支对问题解决的贡献，再用广度优先搜索（BFS）或深度优先搜索（DFS）等算法探索思维树，并进行前瞻和回溯。

反思与改进：ReAct框架

Agent对过去的行动进行自我批评和反思，从错误中学习并改进未来的步骤，从而提高最终结果的质量。实际任务中试错不可避免，自我反思在这个过程中至关重要——它允许Agent通过改进过去的行动决策、纠正以前的错误来进行迭代改进。反思是Agent对事情进行更高层次、更抽象思考的结果，当Agent感知到的最新事件的重要性评分之和超过一定阈值时周期性生成，可以类比"三思而后行"。

《ReAct: Synergizing Reasoning and Acting in Language Models》提出了一种结合推理（Reasoning）和行动（Acting）来增强LLM决策效果的方法。三种模式的对比很能说明为什么要把两者结合：

  • 仅推理（Reasoning Only）：LLM仅基于已有知识推理生成答案——如果LLM本身不具备这些知识，容易出现幻觉，胡乱回答
  • 仅行动（Acting Only）：不加推理，仅用工具（比如搜索引擎）检索——得到的往往是海量资料，不能直接回答问题
  • 推理+行动（Reasoning and Acting）：LLM先基于已有知识并审视拥有的工具，发现知识不足则调用工具获取新信息，再基于新信息重复推理和行动，直到完成任务

ReAct的工作流程是一个循环，每个循环包含三步：Thought（思考）——基于当前状态和目标推理下一步该做什么；Action（行动）——选择合适的工具并执行，获取外部信息或改变环境状态；Observation（观察）——接收行动执行后的结果，作为下一轮思考的输入。这个循环持续到Agent认为任务已完成，最终输出答案。

优点：动态性与适应性（走一步看一步，能根据实时反馈动态调整策略）；可解释性与可控性（每一步思考和行动都被记录，决策过程透明，便于调试和人工干预）；强大的纠错能力（某一步失败时，下一轮思考中能意识到问题并采取补救措施）。
挑战：效率问题——由于需要多次与LLM和外部工具交互，ReAct的执行延迟和API调用成本相对较高，一个复杂任务可能需要5-10轮甚至更多的循环才能完成。

用LangChain构造一个严格遵循ReAct流程的Agent，计算BMI的例子：

# 一个调用LangChain中的Agent，使用ReAct框架的案例——计算人体的BMI
from langchain.agents import create_agent
from langchain_community.chat_models.tongyi import ChatTongyi
from langchain_core.tools import tool

@tool(description="获取体重，返回值是整数，单位千克")
def get_weight() -> int:
    return 90

@tool(description="获取身高，返回值是整数，单位厘米")
def get_height() -> int:
    return 172

agent = create_agent(
    model=ChatTongyi(model="qwen3-max"),
    tools=[get_weight, get_height],
    system_prompt="""你是严格遵循ReAct框架的智能体，必须按「思考→行动→观察→再思考」的流程解决问题，
    且**每轮仅能思考并调用1个工具**，禁止单次调用多个工具。
    并告知我你的思考过程，工具的调用原因，按思考、行动、观察三个结构告知我""",
)

for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "计算我的BMI"}]},
    stream_mode="values"
):
    latest_message = chunk['messages'][-1]

    if latest_message.content:
        print(type(latest_message).__name__, latest_message.content)

    try:
        if latest_message.tool_calls:
            print(f"工具调用： { [tc['name'] for tc in latest_message.tool_calls]  }")
    except AttributeError as e:
        pass

记忆：从人类记忆机制到智能体记忆

人类的记忆机制通常分三层：感觉记忆（保留感官信息的最早阶段，通常只持续几秒钟）、短期记忆（工作记忆）（持续时间较短，暂时存储和处理有限信息，比如记住一个电话号码直到拨完）、长期记忆（可存储大量信息，从几分钟到一生，再分为可有意识回忆的显性记忆——情景记忆与语义记忆，以及无意识的隐性记忆，如骑车、打字这类技能和习惯）。

智能体的记忆机制与之对应：大模型在大量世界知识数据集上预训练，通过调整神经元权重学习理解和生成语言，这个过程可以视为"记忆"的形成，进而形成世界记忆或长期记忆；短期记忆是当前任务执行过程中产生的信息（某个工具或子任务的执行结果），在任务完结后被清空；长期记忆是长时间保留的信息，一般指外部知识库，通常用向量数据库存储和检索。

工具使用

Agent通过学习调用外部API来获取模型权重中所缺少的额外信息，包括当前信息、代码执行能力和访问专有信息源等——这对于预训练后难以修改的模型权重而言非常重要。正如人类通过创造、修改和利用外部工具突破身体和认知的限制，为LLM提供外部工具（计算器、搜索工具、代码执行器、数据库查询工具等）同样能显著提升其能力。

常用概念速查

几个在Agent与RAG系统中反复出现的基础概念：

概念定义
知识库存储知识和信息的系统，分传统知识库和AI知识库；AI知识库与LLM结合，让AI系统更好地利用本地知识响应查询、执行任务
Embedding（嵌入/向量化）将文本转换为数值向量的过程：捕捉语义和语法特征、降低维度、编码语义关系，使语义相似的词汇在向量空间中彼此接近，是信息检索、文本分类、情感分析等任务的基础
RAG（检索增强生成）融合信息检索与文本生成：先从大数据中检索信息，再基于检索结果生成文本，目的是提高生成内容的相关性、准确性和深度，尤其适用于需要广泛知识和深度理解的复杂查询
Finetuning（微调）对预训练模型做进一步训练，用特定领域/任务的数据调整参数使其更适应具体场景，提升精度、降低错误率或提高处理速度
AGI（通用人工智能）人工智能领域的终极目标：一种能够像人类一样跨领域学习、推理和解决问题的智能系统
AIGC（AI生成内容）利用AI技术（尤其是机器学习和深度学习模型）自动生成文本、图像、音乐或视频等内容，通常专注于特定创作任务，不具备AGI的广泛智能和通用学习能力
知识库 Embedding RAG Finetuning AGI AIGC

Prompt工程基础与迭代优化

提示工程（Prompt Engineering，也称In-Context Prompting），是指在不更新模型权重的情况下，如何与大模型交互以引导其行为、获得所需结果的方法。现在的LLM主要分两类：Base LLM是完成"文字接龙"类工作的基础模型；指令型LLM在基础LLM上做了指令微调（Fine-tune），一般采用RLHF方案训练调整，因此在特定任务上有更好的表现。

迭代优化的三步循环

Prompt的优化不是一次写对，而是一个循环：想法 → 实验验证 → 错误分析 → 想法。每一轮错误分析的结论反过来修正下一轮的想法，逐步收敛到可用的Prompt。

Prompt能做什么

用Prompt可以让LLM完成：总结文本（摘要）、推理问题（数学问题、代码问题）、样本的主题分类、提取句子/文章的情感（积极/消极/正向/反向）、翻译、转写文章风格、转写格式（例如HTML转JSON）、扩充句子、在上下文记忆条件下做对话式聊天机器人等。

Zero-shot与Few-shot：从学习范式到工程实践

Zero-shot Learning（零样本学习）：训练阶段不存在与测试阶段完全相同的类别，但模型可以使用训练过的知识推广到测试集中的新类别——这种能力被称为"零样本"学习，因为模型训练时从未见过测试集中的新类别，在模型训练和提示词优化中均有体现。

Few-shot Learning（少样本学习）：模型在学习了一定类别的大量数据后，对于新类别只需要少量样本就能快速学习；对应的one-shot learning（单样本学习），是样本少到为一的特殊情况。

后面三个金融NLP案例，都是基于"Few-Shot + Zero-Shot"的思想设计Prompt：把一批标注好的示例拼接进消息历史里，模型据此在不修改参数的情况下完成分类、抽取、匹配任务——这是Few-shot在工程上最常见的落地形态：不训练模型，用对话历史里的示例做"临时的模式对齐"。

三个金融NLP实战案例

案例来自金融数据分析场景，三大业务任务都通过 qwen3-max（经由DashScope的OpenAI兼容接口调用）完成：金融文本分类、金融文本信息抽取、金融文本匹配。三个任务复用同一种工程模式——把标注示例拼接成"user/assistant"轮次写入 messages，再把真实待处理的文本作为最后一条user消息发送给模型，让模型基于示例做Few-shot式的模式匹配，而不修改模型参数。

任务输入 / 输出Prompt设计要点
文本分类输入一段金融文本，输出所属类别（新闻报道/财务报道/公司公告/分析师报告/不清楚类别）system prompt限定候选类别集合并声明"不清楚的归为不清楚类别"，4条示例作为user/assistant轮次拼接
信息抽取输入非结构化文本，输出结构化JSON（日期/股票名称/开盘价/收盘价/成交量）system prompt声明字段schema和"缺失字段用'原文未提及'表示"，用2条示例展示"文本→JSON"的映射
文本匹配输入两句话，输出"是/不是"（是否表达同一事实）system prompt声明判断标准为"两句话是否匹配"，用4条示例覆盖"是"和"不是"两类

    print(response.choices[0].message.content)

Agent系统设计核心问题

当前Agent前沿的焦点，已经从"让模型更聪明"转移到"让Agent在长程任务中保持有效上下文和可积累的记忆"。过去两年模型推理能力提升显著，但Agent在真实部署中的失败往往不是因为"不会思考"，而是长程任务中的上下文退化——历史信息衰减、关键证据检索不到、局部决策偏离全局目标。ICML 2026上Context Folding的工作把这个问题讲得很直白：Agent在长任务中"只能把有限的前序工作保持在视野内"，任务越长，越慢、越贵、越容易丢掉关键信息。

值得跟踪的方向是主动式上下文管理：一类是让Agent学会"折叠"子任务上下文，完成后只保留结构化摘要，用RL训练Agent自主判断何时分支、何时折叠；另一类是统一图与向量记忆的路由机制，MemWeave在LoCoMo上做到F1 73.5%，同时把延迟降低95.7%、token成本降低90%以上。更前沿的思路是把记忆从"保存历史记录"推进到"从经历中沉淀可复用经验"。

上下文管理能力正在成为Agent从demo走向生产部署的核心瓶颈，而且它把记忆、规划、工具调用三个子问题串在了一起——Agent必须学会主动决定"什么该留在上下文中、什么该归档、什么该丢弃"。

下面是围绕Agent系统设计整理的一组高频技术问答：

1Agent的本质是什么？什么场景适合Agent，什么场景适合固定Workflow？

Agent和写死的Workflow脚本，边界在哪里？分不清楚，很容易把该用规则解决的问题过度设计成一个不可控的Agent。

Agent的本质是"在不确定性环境中做决策并执行的系统"。它和Workflow的核心区别在于——Workflow的控制流是预定义的，Agent的控制流是模型动态决定的。判断标准很简单：如果步骤可以提前穷举，用Workflow；如果步骤依赖实时信息且分支不可穷举，用Agent。

Agent适合检索、规划、多步工具调用这类可验证的重复任务；但涉及高风险决策、强合规约束或无法自动验证结果的场景，必须保留Human-in-the-Loop——比如订单支付、线上变更这类操作，Agent可以做"建议"，但执行必须有人确认。更常见的落地形态是混合模式：主调度用Agent做意图路由和任务规划，子任务尽量沉淀为确定性Workflow，这样既保留灵活性又控制风险。

2Agent中台的编排层和执行层，应该耦合到什么程度？

编排层管得太细，每加一个新能力都要改核心代码；管得太松，又变成什么都不管的黑箱。耦合度怎么拿捏？

倾向于"松耦合的编排层 + 紧耦合的执行层"。编排层保持轻量，只做Agent注册、路由、上下文传递和生命周期管理，不把具体业务逻辑焊进去；执行层（Skill/Tool）可以紧耦合到具体领域，但通过标准协议（如MCP）对外暴露能力。

耦合度的判断依据是变更频率：编排层的接口应该是低频变更的，执行层的实现可以高频迭代。如果发现每次加一个Skill都要动编排核心，说明耦合过度了。要支撑多个C端场景时，编排层还需要考虑多租户隔离和版本灰度能力。

3Agent循环怎么控制？终止条件有哪些？

Agent自己说"我完成了"，能信吗？没有外部校验，它既可能提前收工留下半成品，也可能在原地打转耗光预算。

循环控制设三层终止条件。第一层是硬性边界——最大循环次数（一般5-10轮，视任务复杂度）。第二层是目标完成校验——每轮结束后用轻量级verifier判断"任务是否已完成"，可以是规则引擎或一个小模型，不需要用主模型。第三层是异常检测——重复调用检测（连续两轮调用同一工具且参数相似度超过阈值就中断）、无进展检测（连续N轮没有新增有效信息就中断）。

人工介入的触发点分两类：主动介入（模型输出置信度低于阈值时暂停）和被动介入（超过硬性边界后转人工）。核心设计原则是——Agent不能自己决定"我完成了"，完成判定必须由外部校验器来做。

4Agent开发中最大的挑战是什么？怎么验证Skill修改后能达到线上预期？

代码有单元测试，Agent的回复质量和Skill调用正确性却没有天然的度量标准。改了一个Skill的Prompt，怎么知道它在线上不会变差？

最大的挑战是"效果不可直接度量"。解法是把主观问题拆成可自动化的客观子问题：Skill调用是否正确→用参数匹配+工具返回码校验；任务是否完成→用规则+小模型做二值判定；回复质量→用LLM-as-Judge配合人工抽检校准。

验证Skill修改是否达标，核心是A/B对照+回归测试集：维护一个覆盖核心场景的黄金测试集（Golden Set），每次修改后跑全量回归，关注通过率和badcase分布的变化；如果修改涉及Prompt，还要额外做一轮LLM-as-Judge的偏好对比，看新版本是否在多数case上不劣于旧版本。

5如何看待千问、ChatGPT、豆包、Kimi等产品的能力差异？

同样是大模型驱动的助手产品，差异往往不在模型参数表上，而在工程和场景适配上。

ChatGPT在通用Agent能力（Code Interpreter、多工具编排）上领先；豆包在中文C端交互体验和多模态融合上更顺滑；Kimi的长上下文和文档理解是差异化优势；千问的强项在于中文知识覆盖和电商/本地生活场景的天然数据优势。

千问最应该补齐的短板，不是模型能力，而是Agent的"确定性体验"——用户对C端产品的容错率远低于B端。一个典型痛点是：用户说"帮我查一下附近评分4.5以上的火锅店"，Agent可能调用3次工具都失败了，但只回一句"抱歉我没找到"，用户体验断点在于Agent不暴露"我在做什么、做到哪一步了"。需要补齐的是过程透明化+失败降级策略：让用户看到Agent的推理链路，失败时有明确的fallback路径（比如"工具暂时不可用，我帮你直接跳到搜索页"）。

Agent评测体系怎么从零搭建

6如果从零设计一个Agent评测体系，怎么设计？

评测体系不是一份指标清单，而是一条从数据构造到闭环迭代的完整链路——哪一层没搭好，后面的数字都不可信。

分四层来搭。

第一层：评测集设计。核心原则是分层覆盖——正常流量、边缘case、对抗样本、历史badcase四类按比例分配。人工构建保证覆盖率（约60-70%），线上用户反馈持续补充（30-40%）。每条case要标注预期的关键行为节点（调用了什么工具、参数对不对、最终输出应包含什么），而不是只标注最终答案。

第二层：评测执行。能自动化的坚决自动化——工具调用正确性用规则校验，任务完成度用规则+小模型二值判定，回复质量用LLM-as-Judge配合人工抽检校准。LLM-as-Judge需要定期做一致性校验（与人工评分对比，Kappa系数>0.7才可用）。

第三层：指标定义。不能只看"答对了没有"，要分维度：任务完成率、工具调用准确率、平均轮次、延迟P50/P95、token成本、安全合规通过率，并定义分层的通过标准——有些case允许工具调用不完美但最终结果对，有些则要求链路完全正确。

第四层：闭环迭代。评测结果必须回流到数据合成和训练侧。badcase分析要定位到具体环节（路由错误、规划错误、工具选择错误、参数生成错误、还是输出格式化错误），不同环节的修复策略完全不同。评测报告要能回答"这一版比上一版在哪个维度上变好了、哪个维度变差了"。

7多模态评测集怎么设计？评测执行中有哪些自动化提效的部分？

图片场景多了一层麻烦：'模型看到了什么'和'模型理解了什么'是两件事，badcase出现时得先分清是哪一层的问题。

多模态评测集采用两层标注：感知层标注（图片中有哪些元素、文字、布局关系）和理解层标注（对于给定问题，正确的理解应该是什么）。这样badcase出现时，可以定位是感知问题还是推理问题。

自动化提效的原则是自动化不是替代人工，而是把人工从重复劳动中解放出来去处理真正需要判断力的case。可自动化的部分包括：批量图片预处理和标准化、调用模型跑全量case并收集原始输出、用规则做初步过滤（比如输出格式不符合要求的直接标记为失败）。需要人工介入的是：边界case的判定标准制定、LLM-as-Judge的评分校准、以及badcase的根因分析。

8Agent评测的badcase主要集中在哪些部分？解决思路是什么？

同一类badcase反复出现，如果只是逐个修，修复速度永远赶不上badcase产生的速度。

badcase通常集中在三个区域：工具调用的参数生成错误（模型知道该调哪个工具，但参数不对）、多步任务的上下文丢失（做到第三步忘了第一步的关键约束）、模糊输入的意图误判（用户表达不精确时Agent做了错误假设）。

解决思路按根因分层：参数错误→优化工具定义的schema和示例，必要时加参数校验的二次确认；上下文丢失→引入结构化摘要或关键约束的显式重注入；意图误判→在意图识别层加一层"置信度低于阈值时主动追问"的兜底策略。关键原则是：badcase修复不能只修单个case，要问"这个错误类型会不会在其他case上复现"——修一个case的同时要反向扩充评测集，确保同类问题被覆盖。

9Skill和Tool的区别是什么？

两个词经常被混着用，但如果架构上不区分，Agent的能力边界会越来越模糊。

从工程视角看，Tool是原子能力，Skill是面向任务的组合能力。Tool是最小执行单元（比如"查询数据库""调用搜索API"），Skill是把多个Tool按特定业务逻辑编排成的可复用能力单元（比如"酒店比价"这个Skill可能内部调用了3个Tool）。

区分它们的关键在于复用粒度和变更频率：Tool的接口应该极其稳定，Skill可以随业务迭代。Agent做的是"选哪个Skill"，Skill内部做的是"怎么组合Tool"。如果一个Skill被大量Agent直接调用且逻辑简单，说明它可能应该被降级为Tool；反之如果一个Tool被多个Skill以相同方式组合使用，说明应该沉淀为新Skill。

10模型的上下文压缩怎么做？对话太长了怎么处理？

上下文窗口不是无限的，硬撑一个几十轮的对话在一个上下文里，成本和延迟都会先垮掉。

关注的是分层策略，而不是单一方法：先用工程手段省token，实在不够再考虑模型层面的压缩。具体分四层：

第一层，早期对话压缩成结构化摘要——每隔N轮，用模型把已完成的部分压缩成"用户需求+已确认参数+当前进展"的结构化文本，释放原始token。第二层，大任务拆子任务——一个30步的任务不要在一个上下文里硬撑，拆成5个子任务，中间结果通过外部存储传递。第三层，中间结果落库——工具调用的返回值只提取关键字段存数据库，上下文里只留一句"已完成XX，结果存储在task_123"。第四层，按需召回——建立对话的索引（主题+关键实体），需要时按主题精准召回，而不是全量塞回去。

这个设计的关键取舍是：摘要压缩会丢细节，所以摘要模板的设计必须覆盖"哪些信息丢了一定量级"，这需要靠评测来验证。

11评测集的覆盖度有什么缺陷？线上反馈对优化评测集有什么帮助？

评测集是在理想条件下构造的，但线上用户的输入永远比想象中脏。

评测集最常见的缺陷是"实验室偏差"——评测集在理想条件下构建，但用户真实输入充满噪声、拼写错误、口语化表达、多意图混杂。另一个隐蔽缺陷是"长尾场景的代表性不足"，比如评测集里"查天气"有10条case，但"查天气+设置提醒+分享给朋友"这种组合场景只有1条，而线上组合场景占比可能远超预期。

线上反馈的价值在于它天然覆盖了评测集构建时想不到的场景分布。但直接用线上数据补充评测集也有坑——线上数据是有偏的（高频用户贡献了大量样本），需要做重采样和分层。做法是：线上反馈作为"候选池"，人工筛选后按场景维度分层纳入评测集，同时给线上来源的case标注"来源=线上"，分析时可以和人工构建的case分开看。

12定义Agent评测指标，会关注哪些点？

指标堆得越多不代表评测越靠谱，如果每个指标都答不出"好坏的阈值在哪、变差了怎么定位"，指标本身就是噪声。

把指标分四个象限：效果象限——任务完成率（核心）、工具调用准确率、端到端成功率；效率象限——平均轮次、P50/P95延迟、单次任务token成本；质量象限——输出格式合规率、幻觉率（通过检索溯源或事实校验）、安全合规通过率；体验象限——用户干预率（用户需要手动纠正Agent的次数）、追问率（Agent主动追问的次数，过高说明意图识别有问题）。

关键不是指标数量，而是每个指标都要有明确的"好/坏"阈值和归因路径。比如"任务完成率下降2%"，要能快速定位是哪个环节的指标变了——是工具调用准确率降了，还是平均轮次增加导致了超时。

通用工程问题：幻觉、记忆与多Agent协作

13Agent如何减少幻觉？工业场景怎么做？

幻觉不可能被彻底消除，工业场景真正要解决的问题是让它可控。

工业场景的幻觉治理要分层防御：第一层，检索增强——关键事实必须可溯源，输出附带引用来源，无来源的断言标记为低置信度。第二层，工具验证——对可验证的声明用工具做二次校验（比如"北京今天气温25度"调天气API验证）。第三层，输出约束——用结构化输出（JSON Schema）限制模型能说什么，自由文本部分只允许生成"解释性内容"而非"事实性内容"。第四层，不确定性暴露——当模型置信度低时，明确输出"我不确定"而不是编造。

核心原则是：幻觉不可能消除，但可以检测和降级。工程上要做的是让幻觉的影响可控，而不是追求零幻觉。

14Memory怎么设计？短期记忆和长期记忆怎么落地？

短期记忆和长期记忆各自的存储方式不难理解，难点在于——什么时候把一条信息从短期升级进长期，谁来做这个判断？

短期记忆用滑动窗口+结构化摘要：最近N轮保留原始对话，更早的压缩成结构化摘要（用户需求、关键参数、当前状态）。长期记忆用向量检索+元数据过滤：用户偏好、历史决策模式这类信息存向量库，检索时结合时间衰减和相关性重排。

两者的衔接是设计难点：短期记忆每轮结束后，用一个轻量级分类器判断"这轮对话中是否有值得写入长期记忆的信息"，只有分类器判断有价值的信息才写入长期记忆，避免长期记忆被噪声污染。写入时做去重和冲突检测（同一偏好出现矛盾时标记为"待确认"而非直接覆盖）。

15多Agent/多异步任务下，如何防止上下文污染？

多个子Agent共享同一个全局上下文看起来省事，但一个子Agent的错误假设很容易顺着共享上下文污染到其他子Agent。

上下文污染的本质是不同Agent的"视野边界"不清晰。防止污染的核心设计是每个子Agent只拿到完成自己任务所需的最小上下文，而不是共享全局上下文。

具体做法：主调度Agent维护全局任务状态，子Agent的输入是"任务描述+必要的输入数据"，输出是"结果+状态更新"，子Agent之间不直接共享上下文；如果两个子Agent需要协作，通过主调度Agent做中转，而不是让它们直接对话。另一个关键点是每个Agent的消息历史要独立存储，不能因为复用了同一个LLM session就混在一起。

回过头看，这三份材料横跨的时间不短——从"LLM是什么"的入门笔记，到Prompt工程的具体范式，再到Agent工程化中"如何管理上下文、如何设计可回归的评测体系"这类更接近生产环境的问题。这也是我理解的成长路径：先建立准确的基础概念，再积累可复用的方法论，最后在真实约束（成本、延迟、可验证性）下打磨工程判断力。
