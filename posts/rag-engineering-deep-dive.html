海量文档预处理：先降量，再精洗

文档量大时最容易踩的坑是"硬扛全量精洗"。核心思路应该是：先降量、再分流、然后工程化并行，把算力花在真正有价值的数据上。具体分五步：

第一步：去重——最便宜的大杀器

大文档量里重复内容占比往往高得惊人：同一文档的多个版本、模板化页眉页脚、镜像副本。精确去重用 Hash 就够；近似重复（同一篇文档只改了几个字、换了页眉、调了顺序）需要 MinHash + LSH：先用 MinHash 把每篇文档压成固定长度的相似度指纹，再用 LSH 分桶，把"可能相似"的文档提前圈到同一个桶里，只比桶内候选对，避免全量两两比较。这一步经常能直接砍掉三到七成的量，后面所有环节都跟着省。

MinHash + LSH 近似去重的实现原理

MinHash：把文档切成 shingles（按词/字符切的滑动窗口片段），用 N 个不同的 Hash 函数分别对所有片段取最小值，拼成一个长度为 N 的签名向量。两个文档的 Jaccard 相似度约等于它们签名向量对应位置相等的比例——比签名就是在比相似度，而且签名长度固定，比原始文档小得多。

LSH：有了签名还不够，一万篇文档两两比就是五千万次比较。LSH 把 N 维签名切成 b 个 band（每个 band 有 r 行，b×r=N），只要有一个 band 的哈希值相同，两篇文档就进同一个桶成为候选对，只在候选对里做精确 Jaccard 计算。相似文档的签名在大多数位置都相同，至少一个 band 完全相同的概率很高；不相似的文档很难撞进同一个桶。这样就把 O(n²) 的两两比较降到了只比候选对。b 越大越容易召回（但误报多），r 越大越严格（但可能漏），需要根据业务对召回/精度的要求调参。

文档 → 切 shingles → 多 Hash 取最小 → MinHash 签名
     → 切成 b 个 band → 每个 band 哈希分桶（LSH）
     → 同桶文档作为候选对 → 精确算 Jaccard → 超过阈值判为重复 → 合并/丢弃

实践中通常在文档级和段落级分别做一次：文档级抓多版本、镜像副本；段落级抓模板化页眉页脚、重复段落。去重放在流水线最前面，直接砍量，后面所有环节都省。

第二步：分层分流——不是所有文档都值得同等对待

先做一次轻量预判，把文档分成高、中、低三档：高价值的核心业务文档、FAQ、产品手册走完整清洗加结构识别；一般参考资料走规则清洗加自动结构识别；日志、扫描乱码、低质副本只做粗过滤甚至直接丢。很多项目六成算力其实浪费在根本不会被检索到的文档上。

第三步：流水线并行

清洗不是一个大函数，而是一条流水线：解析、去重、去页眉页脚、结构识别、质量打分、入库，每个阶段独立并行、独立失败重试、幂等。用消息队列加多 worker，或者 Spark、Ray 这类分布式框架，文档量涨十倍加机器就行，不用改逻辑。

第四步：规则优先，模型兜底

八成清洗用正则规则就能搞定——去页眉页脚、去图片占位符、去乱码符号，快且零成本；剩下两成疑难杂症，比如复杂表格还原、版式结构识别，才上布局模型或 LLM 兜底。一上来就 LLM 全量跑，又慢又烧钱。

第五步：增量加缓存

用文档内容 Hash 做缓存键，处理过的直接复用；新文档只跑增量，老文档不重跑；清洗规则版本化，规则升级时只重跑受影响的文档。再加一层质量监控，每个阶段输出质量指标，抽样人工评估，发现某类文档洗得差就单独建规则，而不是拖垮全量。

核心不是追求全量精洗，而是把算力花在真正会被检索到的高价值文档上，用工程化手段保证吞吐和可扩展性——先去重砍量、再分层分流、然后流水线并行、规则优先模型兜底、增量缓存避免重复、最后质量监控兜底。

Embedding / Rerank 模型选型

多语言场景下，Embedding 和 Rerank 的选型经验：

  • Embedding：首选 Qwen3-Embedding-8B 打底，原生支持 100 多种语言，32K 上下文，维度可调，MTEB 多语言榜排名靠前。GPU 预算紧就降到 4B 或 0.6B，多语言基线仍在。
  • Reranker：直接配套用 Qwen3-Reranker-4B，与 Embedding 同源，多语言排序质量有保障，又比 8B 省资源。追求更轻量可选 jina-reranker-v3（0.6B），多语言检索指标比基础版 Qwen3-Reranker-0.6B 更高。
  • 托管方案：选 Cohere Rerank 4，按精度和延迟需求在 Pro / Fast 之间选择。

元数据与关键词匹配在向量数据库中的存在形式

元数据过滤

元数据不会转成向量，它以结构化字段原样存储，过滤走的是传统索引那套——倒排、B-tree、位图，跟向量检索是两条并行路径。执行上分 pre-filtering 和 post-filtering：先按元数据筛出子集再向量检索，或先向量检索再过滤。成熟的向量数据库大多用 pre-filtering，靠标量索引保证过滤效率，这样才能实现"语义相关 + 业务过滤"的组合查询，比如只在产品部最近三个月的文档里做语义搜索。

关键词检索

关键词搜索不是传统数据库那种精确相等匹配，底层是倒排索引加 BM25 相关性打分：先分词，用倒排索引召回包含这些词的文档，再用 BM25 按词频、逆文档频率、文档长度算相关性排序——是带权重的模糊匹配，不是布尔判断。在 RAG 里它和向量检索互补，专有名词、型号、中文术语这些语义表示弱的场景靠它兜底，两路结果用 RRF（Reciprocal Rank Fusion） 按排名融合，避免分数量纲不一致的问题。

RAG 答不准，怎么排查

先从检索侧、生成侧分别分析。手动查看 top-K 检索结果——如果答案在里面，说明是生成侧问题（Prompt、上下文噪声、引用约束、模型能力）；如果答案不在里面，说明是检索侧问题（召回率低、Embedding 选型、Chunk 质量、文档覆盖）。再用 Recall@K 等指标量化，针对性调整。

构造评估集的做法：选取一批"已知有答案的问题"及其对应的正确 chunk，计算 Recall@K（K 通常取 5 或 10）。一般而言，Recall@5 低于 70% 就说明检索侧有明显问题，需要优先优化。

RAG 系统怎么评估

评估的核心是分两层看：检索侧保证"找得到"，生成侧保证"用得好"，最后用线上采用率做最终裁判。没评估的优化都是盲猜。

一、检索侧：能不能找到相关内容

指标定义说明
Recall@K所有相关 chunk 里，top-K 命中了多少第一道防线，Recall 不够，加 Rerank 也救不回来
Precision@Ktop-K 里相关 chunk 占多少低说明噪声多，会稀释模型注意力
MRR第一个相关结果排名的倒数，多查询取平均衡量"最好的有没有排前面"

工程上的平衡：先用大 K（20–50）保 Recall，再用 Rerank 把 Precision 拉回来，最终只传 3–5 个高质量 chunk 给 LLM。

二、生成侧：答案质量怎么衡量（RAGAS 框架）

生成侧难在答案是自然语言、没有标准答案。现在的事实标准是 RAGAS 框架，用 LLM 自动化评四个维度：

维度衡量什么低分意味着
Faithfulness（忠实度）答案能否从上下文推导，有没有幻觉模型在自由发挥，这是 RAG 相比纯 LLM 的核心优势指标
Answer Relevancy（答案相关性）反向生成问题与原问题的相似度答非所问
Context Relevancy（上下文相关性）chunk 中真正有用的句子占比检索或 Chunking 有问题，噪声多
Context Recall（上下文召回）标准答案的关键信息在上下文中出现多少（需 ground truth）关键信息根本没检索到，后面再高也没用

四者关系：Context Recall + Context Relevancy 从生成角度衡量检索质量；Faithfulness + Answer Relevancy 衡量生成质量。Context Recall 是天花板，它低，后面所有指标都白搭。

三、评估集怎么建

  • 人工构造：质量最高、成本最高，核心场景建 50–200 条足以搭 baseline
  • 真实日志采样：质量中等，适合持续监控
  • LLM 生成：成本最低，适合快速搭框架，但问题可能过于理想化

实践建议：先用 LLM 快速搭框架，再用人工建 50–100 条核心场景高质量集，最后用日志持续补充。

四、离线 + 在线，两个都要看

离线评估：测试集上跑指标，可控可重复，指导优化方向。在线评估：真实用户反馈——显式信号有点赞、点踩、纠错；隐式信号有是否追问、是否复制答案、停留时长。

关键坑：离线指标漂亮但线上采用率下降，通常三个原因——测试集偏差、延迟变长用户等不及、答案变八股文用户不爱看。线上采用率是最终裁判，离线指标只是过程指标。

五、评估延迟和成本怎么权衡

RAGAS 四个指标都要调 LLM，一条评估可能额外耗时 1–2 秒，Token 消耗是原问答的 4–8 倍。生产上的分级策略：

  • 高风险场景（约 5%，医疗、法律、金融）：实时全量评估，宁可多花 500ms 防幻觉
  • 中风险场景（约 20%）：只跑 Faithfulness
  • 低风险场景（约 75%）：只记日志，离线评估

这样既保住核心场景质量，P95 延迟也控得住，成本只增加约 15%。

六、评估驱动的优化闭环

  1. 建 baseline：评估集跑一遍，记录所有指标
  2. 定位瓶颈：Recall<70% 优先优化召回；Recall 高但 Precision 低加 Rerank；Context Relevancy 低优化 Chunking；Faithfulness 低改 Prompt
  3. 针对性优化：每次只改一个变量
  4. 对比验证：比 baseline 好就采纳，差就回滚
  5. 持续迭代：新问题加入评估集，定期重评，监控线上
评估分三层：检索侧看 Recall@K/Precision@K/MRR，生成侧用 RAGAS 评四个维度（其中 Context Recall 是天花板），最后看线上采用率这个真实信号。评估集先人工建核心场景，再用日志持续补充；生产上按风险分级评估控制成本；最终形成"建 baseline → 定位瓶颈 → 单变量优化 → 对比验证 → 持续迭代"的闭环。有框架、有数据、有闭环，才是真正做过 RAG 评估。
